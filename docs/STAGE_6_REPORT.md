# Этап 6. TEACHER DASHBOARD — рабочая панель преподавателя — отчёт

Статус: **реализовано и проверено**. Достижения, Зачёт и Progress Check
как модули — не реализовывались (как и требовалось): везде, где ТЗ
самого Dashboard ссылается на их данные (квалификационные баллы,
статус зачёта, промежуточная диагностика), показана честная заглушка,
а не выдуманное число или нулевой график.

## 0. Источник ТЗ

Файл, присланный под именем `English_Start_Profile_LOVABLE_FINAL_SPEC_RU_UI.md`,
оказался побайтово идентичен уже имеющемуся в репозитории
`docs/SPEC.md` — использовал его как единственный источник, отдельной
сверки двух версий не потребовалось.

## 1. Структура Dashboard

`frontend/src/pages/teacher/TeacherHome.tsx` (главная страница
преподавателя, `/teacher`):

1. **Селекторы** Учебный год → Курс → Группа, каскадные (смена года
   сбрасывает курс и группу, смена курса — группу). Списки грузятся
   один раз при заходе на страницу; переключение селекторов работает
   по уже загруженным данным — повторный запрос идёт только за самим
   Dashboard выбранной группы.
2. **Заголовок группы** — название, специальность, курс, учебный год,
   число студентов, «Диагностика завершена: X из Y».
3. **KPI-блок «Состояние группы»** — ровно 6 плиток: диагностика
   завершена (X/Y), средний диагностический результат (число, не
   CEFR), средняя мотивация, средняя самостоятельность,
   квалификационные баллы (честно «Не реализовано»), готовы к зачёту
   (то же).
4. **«Требуют внимания»** и **«Возможности развития»** — рядом, по
   максимум 5 записей каждый.
5. **«Прогресс»** и **«Прогресс по зачёту»** — рядом, оба — честные
   пустые/неполные состояния (модули не реализованы).
6. **Таблица студентов** — поиск, фильтры, сортировка, 11
   столбцов-эквивалентов из ТЗ, на мобильном экране превращается в
   карточки.

Пустая группа (`studentCount === 0`) не показывает KPI/блоки/таблицу
вообще — только «В группе пока нет студентов.» + кнопка «Скопировать
код N» (код берётся из уже загруженного списка групп, не хардкодится).

## 2. Источники каждого показателя

Всё считает backend (`backend/src/routes/teacherDashboard.ts` +
`backend/src/analytics/{scoring,insights}.ts`), фронтенд ничего не
досчитывает — это осознанное решение: сумма/среднее должны совпадать
для Dashboard и для профиля студента, а не в двух разных местах
кода.

| Показатель | Источник |
|---|---|
| Диагностика завершена X/Y | `GroupMembership` (ростер) × `DiagnosticAttempt.status` |
| Средний диагностический результат | `DiagnosticResult.overallPercentage` завершённых попыток, среднее |
| Средняя мотивация / самостоятельность | `QuestionnaireAnswer` по Q15+Q16 / Q21+Q22 (только у ЗАВЕРШЁННЫХ анкет) → `computeMotivation`/`computeAutonomy` |
| Квалификационные баллы / Зачёт (KPI) | `{ implemented: false }` — модуль не существует |
| «Требуют внимания» | комбинация факторов из diagnostic/questionnaire/gap/barriers, см. §3 |
| «Возможности развития» | сильный базовый сигнал + конкретный интерес (Q29/Q33/Q37), см. §4 |
| «Прогресс» | всегда `NOT_CONDUCTED` + рекомендованный срок 5–6 мес. — Progress Check не реализован |
| «Прогресс по зачёту» | `{ implemented: false }` на все 4 подпункта |
| Столбец «Разрыв» | `computeGapCategory(selfAssessment, normalizeDiagnosticToFivePointScale(diagnosticPercentage))` |
| Столбец «Зона развития» | навык с наименьшим % в `skillBreakdown` завершённой диагностики |
| Столбец «Потенциал» | метка из того же расчёта, что и «Возможности развития» |
| Столбцы «Баллы» / «Зачёт» | честный `null` — модуль не реализован |

Методологическая оговорка (полностью раскрыта в комментариях
`analytics/scoring.ts`): формулы для «Мотивация»/«Самостоятельность»
в самой спецификации не даны как число — только перечень вопросов.
Решение: в среднее идут ТОЛЬКО вопросы с однозначной порядковой шкалой
вариантов (Q15/Q16 и Q21/Q22); вопросы-списки причин без порядка
(Q17/Q18/Q20/Q23) в число не превращаются, остаются качественным
контекстом. Тот же принцип, что и «не выдумывать CEFR без матрицы» на
Этапе 5 — только применён к недостающей формуле, а не к недостающему
порогу.

**Производительность (ТЗ п.19).** Dashboard запрашивает у
`QuestionnaireAnswer` только 9 кодов вопросов (`DASHBOARD_QUESTION_CODES`
в `scoring.ts`), а не все 45, и читает уже посчитанный на Этапе 5
`DiagnosticResult`, а не сырые `DiagnosticAnswer`. Полные 45 ответов
анкеты подгружаются только при открытии конкретного профиля студента
(`GET /api/teacher/groups/:id/students/:studentId`).

## 3. Логика «Требуют внимания»

`backend/src/analytics/insights.ts`, `buildAttentionEntry`. Взвешенные
факторы (вес 1 — «сниженный»/«невысокий», вес 2 — «низкий»/«не
завершено»):

- диагностика не завершена (вес 2) / анкета не завершена (вес 1);
- диагностический результат <30% (вес 2) / <50% (вес 1);
- самый слабый навык диагностики <50% (вес 1);
- мотивация <1,8 (вес 2) / <2,5 (вес 1);
- самостоятельность <1,8 (вес 2) / <2,5 (вес 1);
- разрыв самооценка↔диагностика ≥1,5 балла по шкале 1–5 (вес 1);
- 2+ отмеченных барьера в обучении (вес 1).

Флаг ставится только при **суммарном весе ≥2** — единственный слабый
показатель (вес 1) человека в список не добавляет; это проверено
отдельным тестом (см. §5). Исключение — незавершённая диагностика
(вес 2 сама по себе): отсутствие данных всегда требует внимания
преподавателя, это намеренно не «единичный слабый показатель», а
сигнал «мы ничего не знаем об этом студенте».

`primaryReason` — фактор с наибольшим весом (при равенстве весов —
первый по порядку вычисления, детерминированно). Запрещённые слова
(«проблемный/слабый/немотивированный/плохой студент») нигде не
используются — только нейтральные формулировки из самого ТЗ. Данные
блока «Почему?» отдают текстовые формулировки и число (`Диагностический
результат: 42%`), не технические коды вопросов.

Никакого ранжирования: список не сортирует «сильных» и «слабых»
студентов друг относительно друга, порядок — только по убыванию
суммарного веса внутри самого списка «Требуют внимания» (не общий
рейтинг группы).

## 4. Логика «Возможности развития»

`buildOpportunityEntry`. Строится только по студентам с завершённой
анкетой (без неё сигналы интереса неизвестны — не «отсутствуют»).
Требует **сильный базовый сигнал** (мотивация ≥4, самостоятельность ≥4
или диагностика ≥70%) **и** конкретный интерес из Q29/Q33/Q37:
приоритет исследовательский → конференционный → проектный → «высокий
языковой потенциал» (если явного интереса нет, но результат ≥80%).

Система не решает за преподавателя: возвращается только `potentialLabel`
(«Конференционный потенциал» и т.п.) и `reasonText` («Высокая мотивация
+ интерес к конференциям»), без формулировок вида «отправить на
конференцию» — это проверено отдельным тестом на отсутствие слова
«отправить» в ответе API.

## 5. Результаты проверки

**Backend (`npm run verify:dashboard`) — реальные HTTP-запросы,**
5 специально сконструированных студентов с заранее известными
показателями (диагностика управляется точным числом верных ответов по
банку заданий Этапа 5, анкета — точными кодами вариантов):

- KPI считаются из реальных данных (не хардкод): `studentCount`,
  `diagnosticCompletion`, `avgDiagnosticPercentage` (сравнено с ручным
  расчётом), `avgMotivation`; квалификационные баллы/зачёт —
  `implemented: false`;
- студент с 0% диагностики + мотивацией 1,0 + разрывом + барьерами
  → в «Требуют внимания», primaryReason = диагностика;
- студент с ТОЛЬКО незавершённой диагностикой → в «Требуют внимания»
  (вес 2 сам по себе);
- студент с ЕДИНСТВЕННЫМ слабым сигналом (мотивация 2,0, всё
  остальное нейтрально, включая точное совпадение самооценки и
  диагностики) → **НЕ** попал в «Требуют внимания» — правило
  «не флагуем по одному показателю» подтверждено на конкретных числах;
- студент с мотивацией/самостоятельностью 5,0 и интересом к
  конференциям (диагностика 100%, самооценка тоже 5 — без разрыва) →
  в «Возможности развития» с меткой «Конференционный потенциал», и
  НЕ в «Требуют внимания»;
- нейтральный студент — ни в одном из двух блоков;
- запрещённые слова отсутствуют, ранжирования нет;
- таблица студентов — все 5 в наличии, значения по каждому совпадают
  с ожидаемыми;
- пустая группа — честные пустые состояния (`avgDiagnosticPercentage:
  null`, не 0; списки — пустые массивы);
- смена группы возвращает реально разные данные (пустая группа не
  содержит студентов группы А, и наоборот);
- профиль студента — человекочитаемые вопрос/ответ, без кодов вида
  `Q15` в теле ответа; `diagnosticRange` остаётся `null`;
- заметка создаётся и видна в профиле;
- **изоляция:** чужая группа — 404 на Dashboard, на профиль студента,
  на создание заметки; заметка от чужого преподавателя не попадает в БД;
- роль STUDENT не может открыть Dashboard (403); без токена — 401.

Итог: **57 пройдено, 0 провалено.**

Полная регрессия предыдущих этапов — без изменений, всё зелёное:
`verify:access` (11/11), `verify:workspace` (23/23), `verify:onboarding`
(29/29), `verify:questionnaire` (29/29), `verify:diagnostic` (34/34).

**Реальный браузер (Playwright/Chromium)** — полный сценарий через
настоящий UI (форма логина, реальные клики), backend + frontend
запущены как живые процессы:

- вход через форму логина → редирект на `/teacher`, Dashboard
  отрисован реальными данными выбранной группы;
- явный выбор группы через селектор (группы сортируются по дате
  создания по убыванию — при заходе по умолчанию открывается
  последняя созданная, что и обнаружило нужду в этой проверке при
  первом прогоне сценария — см. «Ошибки и находки» ниже);
- переключение на пустую группу → «В группе пока нет студентов.» +
  кнопка «Скопировать код…», данные предыдущей группы не видны;
- переключение обратно → данные группы А возвращаются (не пустой
  кэш);
- переход «Открыть профиль» из блока «Требуют внимания» → реальная
  навигация на страницу профиля, без кодов вопросов на экране;
- **мобильная адаптация (375px):** таблица скрыта, карточки видны,
  горизонтального скролла всей страницы нет;
- поиск по несуществующему имени → честное «По заданным фильтрам
  студентов не найдено.»;
- модалка «Добавить заметку» — заполнение и сохранение через реальный
  клик.

Все 20 сценариев браузерной проверки — зелёные.

### Ошибки и находки в процессе проверки

- **Переполнение плитки KPI.** Значение «Не реализовано» в кегле
  `text-xl` не помещалось в узкую плитку (6 колонок на десктопе, 2 на
  мобильном) и накладывалось на соседнюю — обнаружено визуально по
  скриншоту первого прогона, не текстовой проверкой. Исправлено:
  нечисловые (длинные) значения плитки рендерятся меньшим кеглем.
- **Обрезание ссылки «Открыть профиль».** В блоках «Требуют внимания»/
  «Возможности развития» длинная строка без пробелов (email — запасное
  отображаемое имя студента без заполненного ФИО) не переносилась и
  выталкивала соседнюю ссылку за пределы карточки на мобильном экране.
  Тоже найдено по скриншоту, не автоматической проверкой (проверка на
  отсутствие горизонтального скролла всей страницы её не поймала — то,
  что не переполняет `<body>`, ещё может переполнять карточку внутри).
  Исправлено: перенос строк для длинного текста, ссылка переходит на
  отдельную строку при недостатке места.
- **Скрытый допущение о группе по умолчанию.** Первый черновик
  E2E-сценария предполагал, что при заходе выбрана первая созданная
  группа — на самом деле список групп (как и в API Этапа 2)
  отсортирован по дате создания по убыванию, поэтому по умолчанию
  открывается последняя. Не баг продукта — использовать «последнюю
  активность» как default для селектора разумно, — но исправление
  потребовалось в самом тестовом сценарии, который сначала ошибочно
  зафиксировал это как найденную проблему.

## 6. Проверка прав доступа (сводно)

Все проверки — прямыми HTTP-запросами к реальному API, не через
скрытие пунктов меню:

- Dashboard/профиль студента/заметки чужой группы → 404 (не 403 —
  нельзя отличить «не ваша группа» от «такой группы нет»);
- создание заметки от имени чужого преподавателя — 404, и такая
  заметка не появляется в БД;
- роль STUDENT не может вызвать ни один из маршрутов Dashboard — 403;
- без аутентификации — 401.

## 7. Проверка смены групп (сводно)

- KPI, списки «Требуют внимания»/«Возможности развития» и таблица
  студентов пересчитываются заново при каждой смене группы — старые
  данные не остаются на экране (ни в бэкенд-тесте, ни в браузере);
- данные разных групп одного преподавателя не смешиваются (пустая
  группа Б не содержит студентов группы А, и наоборот);
- данные разных преподавателей изолированы (см. §6).

## 8. Открытые вопросы к следующим этапам

- **Квалификационные баллы и Зачёт.** Модуля начислений/зачёта в
  приложении по-прежнему нет — везде, где ТЗ Dashboard ссылается на
  эти данные, стоит `implemented: false`/`null`, а не выдуманное
  число. Когда модуль появится, потребуется заменить эти места на
  реальные запросы — архитектурно Dashboard уже готов принять их (поля
  зарезервированы в ответе API).
- **Progress Check.** Блок «Прогресс» всегда показывает
  «ещё не проводилась» — это дословно честное состояние, а не
  недоделанная функциональность самого Dashboard: сам Progress Check
  как модуль не реализовывался ни на одном из этапов.
- **Лимит 5 записей в «Возможности развития».** ТЗ явно ограничивает
  только «Требуют внимания» пятью записями; для «Возможности развития»
  такого ограничения в тексте нет — применил тот же лимит по аналогии
  (не перегружать первый экран), это осознанное решение, а не
  найденное в спецификации требование.
- **Фильтр «Диагностический диапазон».** Поскольку утверждённой
  матрицы CEFR-порогов нет (см. Этап 5), диапазоны в фильтре — это
  процентные полосы (до 50% / 50–79% / 80%+), честно подписанные как
  проценты, а не как CEFR-уровни.

Автоматически к следующему этапу не переходим — ждём подтверждения.

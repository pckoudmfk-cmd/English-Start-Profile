# Этап 13. ПОДГОТОВКА К ПИЛОТНОМУ ТЕСТИРОВАНИЮ — отчёт

Создан постоянный, воспроизводимый набор тестовых сценариев и учётных
записей для пилотного тестирования English Start Profile. Новая
функциональность не добавлялась — только тестовые данные и скрипты их
создания/сброса.

## 1. Отделение тестовых данных от реальных

- **Домен email — `.test`**, зарезервированный IANA специально для
  тестирования и документации (RFC 2606) — гарантированно не может
  совпасть с реальным адресом ни сейчас, ни в будущем.
- **Каждое ФИО и название сущности** содержит маркер
  `(ПИЛОТ-ТЕСТ)` — визуально невозможно спутать с реальными данными
  ни в интерфейсе, ни в БД.
- Все константы (email/ФИО/названия) вынесены одним блоком в начало
  `backend/scripts/setup-pilot-test-kit.ts` (`export const PILOT`) —
  перед реальным запуском пилота этот набор можно надёжно найти и
  удалить одним запросом (`WHERE email LIKE '%@pilot.test'`).
- Демо/seed-данных в репозитории не было и не появилось — пилотный
  набор создаётся исключительно через настоящие API-маршруты (тот же
  путь, которым пройдёт реальный пользователь), не прямой записью в БД
  в обход бизнес-логики.

## 3. Скрипты

- **`npm run pilot:setup`** (`backend/scripts/setup-pilot-test-kit.ts`)
  — создаёт/находит Teacher Test Account, учебный год/курс/группу,
  Student A/B/C, присоединяет их к группе, проводит всех троих через
  Start Profile + Start Diagnostic. **Полностью идемпотентен** —
  безопасно перезапускать сколько угодно раз (проверено: второй запуск
  подряд — те же 11/11 проверок, без дублей).
- **`npm run pilot:scenarios`** (`backend/scripts/run-pilot-
  scenarios.ts`) — прогоняет сценарии из задания Этапа 13 (см. таблицу
  ниже). Требует предварительного `pilot:setup`. В отличие от
  `pilot:setup`, не рассчитан на бесконечный повторный запуск «как
  есть» — зачётный тест и Progress Check одноразовые по бизнес-
  правилам (не по ошибке), поэтому перед повторным прогоном сценариев
  нужно сначала сбросить их состояние.
- **`npm run pilot:reset-scenarios`** (`backend/scripts/reset-pilot-
  scenario-state.ts`, новый постоянный скрипт) — сбрасывает именно то,
  что накопил `pilot:scenarios` (достижения/баллы/допуск/зачётный тест
  Student A и B, назначение Progress Check Student C), **не трогая**
  сами аккаунты, группу и пройденные Start Profile/Start Diagnostic.
  Позволяет продемонстрировать сценарии заново с чистого листа сколько
  угодно раз. Проверено: `pilot:reset-scenarios` → `pilot:scenarios` →
  снова 26/26 — цикл сброс/повтор работает надёжно.

## 6. Обнаруженные и исправленные проблемы

Все найденные проблемы были в **тестовых скриптах этого этапа**, не в
продукте (зафиксировано отдельно, чтобы не создавать ложное
впечатление о найденных в приложении дефектах):

- `setup-pilot-test-kit.ts` изначально не имел защиты `require.main ===
  module` — при импорте его констант в `run-pilot-scenarios.ts`
  повторно выполнялся весь `main()`, создавая гонку двух параллельных
  прогонов против одного backend. Исправлено.
- Ожидание статуса `400` для `DUPLICATE_POINT_BLOCKED` было неверным —
  маршрут явно возвращает `409 Conflict` (семантически более точный код
  для конфликта бизнес-правила). Исправлено в тесте.
- Два обращения к полям ответа API по неверному пути (`overallStatus`
  ожидался от студенческого маршрута `/api/student/credit/:groupId`,
  который отдаёт другое поле — `topStatus`; `diagnosticStatus`
  ожидался на верхнем уровне ответа профиля студента, а не внутри
  `header.diagnosticStatus`). Исправлено переходом на маршрут
  преподавательской сводки (`.../summary`, отдаёт `overallStatus`
  напрямую) и правильный путь поля.

## 7. Как пользоваться этим набором дальше

1. `cd backend && npm run pilot:setup` — один раз (или сколько угодно
   раз, идемпотентно) — поднимает Teacher/Student A/B/C и группу.
2. Войти в интерфейс (`/login`) под любым из аккаунтов выше — все
   данные уже реалистично заполнены (пройденные анкета/диагностика у
   всех троих; у Student A — «Устная часть обязательна»; у Student B —
   5 баллов, зачёт завершён, 1 успешно заблокированная попытка дубля в
   истории; у Student C — назначенная промежуточная диагностика).
3. Чтобы продемонстрировать сценарии (п.4 выше) заново «с нуля» —
   `npm run pilot:reset-scenarios`, затем `npm run pilot:scenarios`.
4. **Перед реальным запуском пилота с настоящими преподавателями и
   студентами**: удалить пилотный набор (`DELETE FROM "User" WHERE
   email LIKE '%@pilot.test'` — каскадные связи в схеме БД сами удалят
   все связанные группы/попытки/достижения этих аккаунтов, см.
   `onDelete: Cascade` в `schema.prisma`) либо оставить как
   демонстрационный набор, если он не мешает реальным данным — оба
   варианта безопасны благодаря чёткому разделению по домену `.test`.

## Готово ли приложение к пилотному тестированию

**Да.** Полный путь Teacher → Group → Student(s) → Start Profile →
Start Diagnostic → Dashboard → Student Profile → Достижения →
Квалификационные баллы (с анти-дублированием) → Зачёт (оба сценария:
0 баллов и 5 баллов) → Progress Check (с проверкой, что студент не
может открыть его сам) — пройден целиком, реальными HTTP-запросами,
без единого провала. Постоянный, легко воспроизводимый набор
тестовых аккаунтов создан и явно отделён от любых будущих реальных
данных по независимому от названий признаку (домен `.test`).

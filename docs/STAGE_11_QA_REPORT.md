ограниченный срок жизни, хранится только хэш) — см. CRITICAL №1 ниже
про единственную найденную проблему в этом узле.

**RBAC — три роли (§3).** `requireRole()` на каждом роутере
(инвентаризация подтвердила: все 16 файлов маршрутов, кроме `auth.ts`,

ни один `PUT`-маршрут профиля не позволяет изменить `role` — путь
эскалации привилегий отсутствует структурно. Административной панели
не существует (архитектурно зарезервировано, не реализовано — честно,
это не ошибка Этапа 11).

**Критический security-тест и Direct URL test (§4–5).** Полная матрица
Teacher A/B × Student A/B × прямая подмена id в URL проверена для ВСЕХ
модулей: групп/курсов/лет (`verify-workspace-isolation.ts`), профиля
студента и всех его вкладок — обзор/анкета/диагностика/цели/заметки

сущность (нельзя перебором URL узнать даже сам факт существования
чужого ресурса). Два обнаруженных при инвентаризации пробела в
покрытии (IDOR на attemptId Start Diagnostic и анкеты) — закрыты новым
`verify-qa-audit-security.ts`, оба **подтверждены защищёнными** (404).

**Join Code lifecycle (§8).** Valid/invalid/disabled (410
`CODE_DISABLED`)/expired (410 `CODE_EXPIRED`, отдельное сообщение от

**Анкетирование и Start Diagnostic (§9–11).** Полное покрытие (63

исторические попытки не перезаписываются (`@@unique([studentId,
groupId, kind])` на уровне БД, не только в коде маршрута).

**CEFR-уровни (§12).** Прямая проверка кода (а не только текста в
интерфейсе): `grep` по всей кодовой базе (frontend+backend) на
`A1|A2|B1|B2|CEFR` — единственное реальное использование этих меток:
внутреннее поле `targetLevel` банка заданий (используется только при
СОСТАВЛЕНИИ заданий, никогда не попадает в сериализацию ответа API —
проверено: не встречается ни в `publicView.ts`, ни в `scoring.ts`, ни в
любом `routes/student*.ts`). `diagnosticRange` в схеме БД — строго
`String?`, нигде не заполняется (только читается как `null`). Все
экраны результата содержат явную оговорку «не официальный уровень
CEFR». Выдуманной точности — нет.

**Start vs Progress (§13–15).** `verify-progress-check.ts` содержит
прямой сценарий: Start заморожен на своём результате, Progress
считается отдельным snapshot (`kind="START"` vs `kind="PROGRESS"`,
раздельные строки БД), сравнение в отчёте студента/преподавателя
считается по обеим записям без изменения первой. Студент не может
запустить Progress Check сам (структурно нет `POST`-маршрута создания
попытки на его стороне — только чтение уже назначенной преподавателем),
открыть раньше периода (403 `TOO_EARLY`), изменить дату (нет такого
маршрута у студента) или повторно открыть завершённую попытку на
редактирование. Form A/Form B — 32+32 задания, нулевое пересечение по
id (`b-`-префикс), идентичное распределение по 4 навыкам/сложности.

**Достижения, квалификационные баллы, анти-дублирование (§16–21).**
Все 6 статусов присутствуют дословно (`ACHIEVEMENT_STATUSES`). Балл
начисляется **только** явным решением преподавателя (`action=CONFIRM`
→ 1, `CONFIRM_NO_POINT` → 0) — единый расчёт, статус и
`QualificationPoint` меняются в одной транзакции (невозможно оказаться
в состоянии «подтверждено, но без балла» или наоборот). Анти-дубль —
на **двух уровнях**: (1) предупреждение при создании второй записи с
совпадающим названием+датой+группой+студентом (не блокирует), (2)
жёсткая блокировка в момент начисления второго балла за то же
мероприятие (`DUPLICATE_POINT_BLOCKED`) — подтверждено и то, и другое.
Повторный вызов подтверждения — идемпотентен на уровне БД
(`QualificationPoint.achievementId @unique`, P2002 = «уже начислено»,
не ошибка; прямая попытка второй вставки в обход HTTP проверена в
`verify-achievements.ts`). Правило «5 баллов → устная часть
освобождена» — `qualificationPoints >= 5`, запись `OralAssessment
(EXEMPTED)` создаётся идемпотентно и сохраняется для истории даже если
баллы позже отозваны.

**Кол-во баллов по типу мероприятия (§18) — см. отдельное примечание.**
Спецификация методички Этапа 11 предполагает фиксированную таблицу
(«Participant → 0, Prize → 1, Published → 1, Winner → 1»). Мастер-
спецификация (`docs/SPEC.md`, §30.3) **прямо запрещает** приложению
самостоятельно придумывать такую таблицу («В исходном документе нет
таблицы распределения баллов… приложение НЕ должно самостоятельно
придумывать…») и явно поручает эту таблицу будущей административной
панели (не реализована ни на одном этапе, архитектурно отложена).
Реализованное поведение — точное следствие этого пункта ТЗ: балл
целиком определяется явным решением преподавателя, `claimedResult`
никогда не конвертируется в балл автоматически. **Это не найденная
ошибка — это фиксация конфликта между заданием на аудит и мастер-
спецификацией**, как и просит методичка аудита в п.1 («если
обнаружишь несоответствие спецификации, зафиксируй его»). Менять
методическую логику самостоятельно не стал.

**Зачёт (§22–25).** Результат теста — только `X / N` (проверено:
`answerSchema` принимает исключительно `selectedOptionIndex`,
корректность всегда вычисляется сервером по сохранённому снимку
`correctOptionIndexSnapshot`, никогда не читается из тела запроса —
подтверждено новым тестом попытки подсунуть `correct: true`). Устная
часть — `finalGrade` строго `z.enum(FINAL_GRADES)` (4 значения:
Неудовлетворительно/Удовлетворительно/Хорошо/Отлично), назначает и
подтверждает **только** преподаватель (проверено: попытка передать
`"SUPER_EXCELLENT"` — 400 `VALIDATION_ERROR`, не принято молча).
«Итог» зачёта — единая функция, точное IF/ELSE ТЗ. История (попытки
теста/оценки/решения) не удаляется — только новые строки/новые
`CreditAuditLog`-записи, текущий статус пересчитывается, а не
переписывает прошлое.

**Teacher Dashboard, Student Profile, рекомендации, цели, заметки
(§26–30).** KPI считаются одним батчем без N+1 (см. PERFORMANCE ниже).
«Требуют внимания»/«Возможности развития» — многофакторная логика с
раскрываемым основанием: каждый `factor` несёт `dataLines` с реальным
числом («Аудирование — зона развития» → `dataLines: ["Listening —
43%"]`), не голословно. Все 8 вкладок профиля студента передают
`groupId`+`studentId` и проверены на изоляцию (чужой преподаватель —
404 на каждой вкладке отдельно). Статус цели меняет **только**
преподаватель (единственная точка записи в БД — `teacherStudentProfile

`StudentGoalStatus` автоматически) — «выполнено» никогда не
выставляется системой. `TeacherNote` — ни один student-маршрут и ни
одна student-страница не обращаются к этой модели вообще (не то что
скрыто в интерфейсе — структурно недостижимо с роли STUDENT).

**Язык интерфейса (§31).** Целевой grep по всей кодовой базе на
буквальные `Dashboard/Save/Cancel/Loading/Achievement/Credit/Error/No
data/Submit` как видимый JSX-текст — ноль совпадений. Более широкий

находка — слово «Email» как отдельная подпись поля на 4 экранах
(вход/регистрация/восстановление доступа/профиль студента) — оставлено
без изменений: это устоявшийся в русских интерфейсах (Госуслуги,
банки) частично натурализованный термин, не относится к примерам из
методички; решение задокументировано, а не исправлено молча.

**Mobile/Desktop (§32–33).** У каждого модуля есть собственная
проверка на 375px (регистрация+присоединение, анкета, диагностика,
достижения, зачёт, Progress Check — все стадии 4–10) — отсутствие
горизонтальной прокрутки, доступность кнопок в пределах экрана,
реальные скриншоты. Desktop (1280×900) — весь teacher-флоу проверен

Анкета → Диагностика → Результаты → Достижения → Зачёт → Progress» ОДНИМ
непрерывным мобильным браузерным прогоном (буквально как в п.32
методички) — не прогонялся; см. MEDIUM №3.

**Empty states и обработка ошибок (§34–35).** Формулировки пустых
состояний близко совпадают с примерами методички («В группе пока нет
студентов.», «Пока нет достижений.», «Промежуточная диагностика ещё не
проводилась.», «Стартовая диагностика: не пройдена»). Глобальный
backend error-handler отдаёт только `{error, message}` на русском,
`console.error` — только в серверный лог, стектрейс клиенту не
попадает никогда (проверено чтением `index.ts`). Единственный ответ
без `message` (общий 404 несуществующего API-маршрута) — исправлен в
рамках аудита (см. LOW №1).

**Data Integrity — DB-констрейнты (§36).** Полная инвентаризация
`schema.prisma`: `User.email @unique`, `GroupMembership @@unique(
[studentId, groupId])` (нет дубля membership), `GroupJoinCode.code
@unique`, `QuestionnaireAttempt`/`DiagnosticAttempt @@unique([studentId,
groupId, kind])` (нет второй попытки START/PROGRESS), `QualificationPoint
.achievementId @unique` (нет второго балла), `CreditTestAttempt @@unique(
[studentId, groupId, attemptNumber])`, `OralAssessment @@unique([
studentId, groupId])` и т.д. — все критичные для целостности пары
защищены на уровне БД, не только кода маршрута. Orphan-записи
структурно исключены иначе: в приложении нет ни одного маршрута
жёсткого удаления родительской сущности (User/Group/Course/Year) —
единственные три `DELETE`-маршрута во всём backend узко ограничены
(черновик достижения своего автора, файл доказательства, файл заявки
на допуск), поэтому каскадные связи (`onDelete: Cascade`, тоже
проверено на каждой модели) на практике не запускаются вовсе.

**Business Logic — переходы состояний.** Все ключевые расчёты (баллы,
статус зачёта, статус освобождения от устной части, «Итог»,
диагностический процент, сравнение Старт→Сейчас) вычисляются **одной**
функцией, переиспользуемой между Dashboard/профилем/студенческой и
преподавательской сторонами — не продублированы, не могут разойтись.

## CRITICAL — требует немедленного исправления

### 1. Токен восстановления пароля возвращается в теле API-ответа безусловно (полный захват аккаунта по email)

**Файл:** `backend/src/routes/auth.ts`, маршрут `POST /api/auth/forgot-password` (строка 134).

**Проблема:** `res.json({ ...genericResponse, devToken: token })` — токен сброса
пароля попадает в JSON-ответ **всегда**, независимо от окружения (нет
проверки `NODE_ENV`/любого другого гейта). Также пишется в
`console.log`. Комментарий в коде честно признаёт: «Перед
продакшн-использованием нужно подключить реальную отправку письма и
убрать токен из ответа» — но сам гейт не реализован ни на одном этапе.

**Сценарий атаки:** любой аноним, зная (или угадав по шаблону
`имя.фамилия@колледж`) email преподавателя или студента, вызывает
`POST /api/auth/forgot-password {email}`, получает `devToken` прямо в
ответе, вызывает `POST /api/auth/reset-password {token, newPassword}` —
и полностью захватывает чужой аккаунт (включая преподавательский, со
всеми группами/оценками/баллами) без единого шага, требующего доступа
к почте жертвы.

**Не исправлено в рамках этого аудита** — по явному правилу методички
(«не исправлять молча Critical») и потому, что это узел аутентификации
(изменения в нём — не «очевидная мелкая UI/UX-ошибка»). Требует
согласования: минимальный фикс — убрать `devToken`/`console.log` из
ответа production-сборки (`if (process.env.NODE_ENV !== "production")`)
до появления реального email-провайдера; корректный фикс — подключить
реальную отправку письма и полностью убрать токен из HTTP-ответа
(оставить только в server-side логе, если вообще).

## MEDIUM — желательно исправить

### 1. SQLite как единственный реально работающий провайдер БД — переход на Postgres требует правки схемы, не только `.env`

`backend/prisma/schema.prisma`: `datasource db { provider = "sqlite" }`
— литерал, не читается из окружения (Prisma требует статичную строку
для `provider`). `.env.example` при этом обещает: «для продакшена
укажите строку подключения Postgres» — что не сработает без изменения
самой схемы и повторной миграции. Для пилота с одной-двумя группами
SQLite (в WAL-режиме) справится; при реальном одновременном нагрузке
многих групп/сотен студентов — потенциальные задержки записи (SQLite
сериализует запись на уровне файла). Нужно явно решить до
масштабирования пилота: либо держать SQLite и убрать вводящее в
заблуждение упоминание Postgres, либо подготовить реальный
Postgres-путь (переключение `provider`, миграция, тест).

### 2. Таблица студентов Dashboard не пагинирована и не виртуализирована

`frontend/src/pages/teacher/TeacherHome.tsx` — поиск/фильтр/сортировка
полностью на клиенте поверх `dashboard.students` (весь ростер группы
приходит одним ответом `GET .../dashboard`, без параметров
пагинации/поиска на backend). Backend-агрегация сама по себе не имеет
N+1 (подтверждено чтением `analytics/teacherAccess.ts` — комментарий
в коде прямо заявляет "не N+1", один `findMany` на модель на весь
переданный ростер) — но при группе в сотни-тысячу студентов (§37
методички упоминает 1000 как верхнюю границу теста) весь посчитанный
набор строк (включая `skillBreakdown` на каждого) уйдёт в одном ответе
и будет отрисован в DOM целиком. Для реалистичного размера учебной
группы (15–35 человек) это не проблема; для стресс-теста на 1000 —
да.

### 3. Continuous mobile E2E (весь студенческий путь одним прогоном) не выполнялся

Каждый модуль (Этапы 3–10) по отдельности проверен на 375px реальным
браузером — но именно последовательность «Регистрация → Join →
Анкета → Диагностика → Результаты → Достижения → Зачёт → Progress»
одной сессией одного мобильного браузера (буквально как сформулировано
в §32) не прогонялась в рамках этого аудита. Риск оцениваю как низкий
(все компоненты используют один и тот же слой вёрстки/один и тот же
набор проверенных паттернов), но это не то же самое, что фактически
подтверждённая непрерывность — честно отмечаю как непокрытое, а не
выдаю за пройденное.

### 4. Изменение курсовых настроек зачёта не пишется в `CreditAuditLog`

`PUT /api/teacher/credit/courses/:courseId/settings`
(`maxTestAttempts`/`revealCorrectAnswers`) не создаёт запись в
`CreditAuditLog` — в отличие от всех per-student решений (допуск/тест/
устная часть), которые полностью покрыты историей. Это курсовая, не
per-student настройка, поэтому риск ниже, чем у отсутствия истории
решений по конкретному студенту (которой, для сравнения, вообще нет
пробелов) — но раздел §39 методички требует историю «важных действий
преподавателя» без исключения для курсовых настроек.

## SECURITY — итог

**Найдено:** 1 Critical (см. выше — токен восстановления пароля).
**Всё остальное — подтверждено защищённым** прямыми HTTP-запросами
(430 проверок), включая специально добавленные для этого аудита:

- IDOR на attempt-id Start Diagnostic и анкеты (студент B угадывает id
  попытки студента A) — 404 на чтение/ответ/завершение/результат;
  собственная попытка студента B не содержит «просочившихся» данных.
- Полная матрица Teacher A/B × Student A/B на всех модулях (группы,
  профиль, диагностика, анкета, достижения, зачёт, Progress Check) —
  404 на чужую сущность, никогда 403 (не даёт узнать сам факт
  существования).
- Подмена cookie другого пользователя не даёт доступа к чужим данным.
- Попытки протащить в теле запроса сервер-вычисляемые поля
  (`qualificationPoint=99`, `points=99`, `studentId`, `correct=true`,
  `finalGrade` вне 4 уровней) — все отклонены или проигнорированы,
  реальное значение всегда определяется сервером.
- Student не может вызвать ни один teacher-маршрут (включая назначение
  Progress Check от своего имени) — 403.
- JWT: секрет обязателен (приложение отказывается стартовать без
  `JWT_SECRET`, нет слабого дефолта), httpOnly-cookie, `COOKIE_SECURE`
  — управляемый флаг для прода (задокументирован в `.env.example`).
- Ответ на неверный email при входе идентичен ответу на неверный
  пароль (нет перебора зарегистрированных адресов через `/login`).
  Тот же принцип у `/forgot-password` — но нарушается самим
  `devToken` (см. Critical №1: генерическое сообщение соблюдено,
  а вот сам токен — нет).

## DATA INTEGRITY — итог

Все критичные для целостности пары полей защищены **на уровне БД**
(`@@unique`), не только в коде маршрута — подтверждено чтением полной
схемы: нет дубля membership, нет второй попытки START/PROGRESS
диагностики или анкеты на пару (студент, группа), нет второго
квалификационного балла за одно достижение, нет второй попытки
зачётного теста с тем же номером, нет второй записи устной части.
Orphan-записи структурно исключены — родительские сущности
(пользователь/группа/курс/год) никогда не удаляются приложением
(архивирование, не удаление); единственные 3 маршрута `DELETE` во всём
backend узко скоуплены и не создают риска осиротевших связей.
Audit-трейл (`AchievementAuditLog`, `CreditAuditLog`,
`StudentGoalStatusEvent`) несёт actor/timestamp/previous value/new
value/action на каждой записи, кроме курсовых настроек зачёта (см.
MEDIUM №4).

## BUSINESS LOGIC — итог

- **Диагностика:** отдельность анкеты/теста, серверный расчёт
  правильности и процента, разбивка по 4 навыкам — корректно; никакой
  выдуманной CEFR-точности.
- **Достижения:** 6 статусов, единая транзакция статус+балл, анти-
  дублирование на двух уровнях (предупреждение + жёсткая блокировка),
  идемпотентность на уровне БД — корректно. Балл не выводится
  автоматически из заявленного результата — намеренное и спецификацией
  предписанное поведение (см. фиксацию несоответствия методички
  аудита и `SPEC.md` §30.3 выше), не ошибка.
- **Квалификационные баллы:** 5-балльное правило освобождения —
  корректный порог, идемпотентное создание записи освобождения,
  история сохраняется при отзыве баллов.
- **Зачёт:** результат теста — только X/N, не превращается в оценку
  автоматически; устная часть — строго 4 уровня, только преподаватель;
  «Итог» — единая функция с точным деревом ТЗ.
- **Progress Check:** Start никогда не перезаписывается, Form A/Form B
  без пересечений, доступ строго по назначению+периоду.

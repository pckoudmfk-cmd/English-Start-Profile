# Этап 8. ДОСТИЖЕНИЯ, ВНЕАУДИТОРНАЯ ДЕЯТЕЛЬНОСТЬ, КВАЛИФИКАЦИОННЫЕ БАЛЛЫ — отчёт

Статус: **реализовано и проверено**. Ни одно из явных ограничений ТЗ
(п.36) не нарушено: один-единственный вид балла, ровно 1 за
результативное мероприятие, никаких баллов за посещение/сертификат
участника/волонтёрство, никаких коэффициентов.

## 1. Какие сущности созданы

`backend/prisma/schema.prisma`:

- **`Achievement`** — заявка студента: студент/группа/курс/учебный год
  (снимок на момент создания, тот же приём защиты в глубину, что и у
  `QuestionnaireAttempt`), данные мероприятия, заявленный результат,
  `status` (6 значений из ТЗ п.7), денормализованный кэш
  `qualificationPoint` (0/1), решение преподавателя (`teacherId`,
  `teacherComment`, `verifiedAt`).
- **`AchievementEvidence`** — подтверждающие документы (может быть
  несколько на одно достижение); хранит только метаданные, сами файлы —
  на диске (`backend/uploads/achievements/<achievementId>/`, вне
  репозитория).
- **`QualificationPoint`** — начисленный балл. `achievementId`
  **уникален** — это и есть защита от повторного начисления на уровне
  БД (п.3 ниже).
- **`AchievementAuditLog`** — append-only журнал (создание, отправка,
  правка, добавление/удаление документа, запрос уточнения,
  подтверждение (с баллом/без), начисление балла, отклонение, отзыв
  статуса, отзыв балла) — кто, когда, старое/новое значение, причина.

`backend/src/analytics/qualification.ts` — **единая** функция расчёта
(ТЗ п.23): `computeOralPartStatus(points)` (≥5 → `EXEMPTED`),
`getStudentQualificationSummary`, `getGroupQualificationPointsByStudent`,
`getGroupAchievementsSummary`. Используется отовсюду (Dashboard, Student
Profile) — расчёт не продублирован.

## 2. Логика начисления

`backend/src/achievements/service.ts`, `applyTeacherDecision` — единая
функция для всех 5 решений преподавателя (4 прямых + «Изменить
статус»), выполняется в одной транзакции Prisma:

1. проверяет, что действие допустимо из текущего статуса (4 прямых
   решения — только из `PENDING`; «Изменить статус» — только из уже
   проверенного);
2. требует комментарий, где ТЗ (п.11, 30) его требует: «без балла»,
   «уточнение», «отклонить», «изменить статус» — не требует только
   «Подтвердить — 1 балл»;
3. **до** записи проверяет дубль-с-баллом (см. §4);
4. меняет статус достижения и `qualificationPoint`;
5. создаёт или удаляет `QualificationPoint` — **в той же транзакции**,
   что и смена статуса: невозможно оказаться в состоянии «CONFIRMED без
   балла» или «не-CONFIRMED с баллом»;
6. пишет запись(и) в `AchievementAuditLog`.

Заявленный студентом результат (`claimedResult`) никогда не
конвертируется в балл автоматически (ТЗ п.32) — единственный путь к
`QualificationPoint` — явное решение преподавателя.

## 3. Защита от повторного начисления

Два независимых уровня, оба проверены тестом:

- **Уровень БД**: `QualificationPoint.achievementId` — `@unique`.
  Прямая попытка вставить вторую запись для того же `achievementId`
  (в обход HTTP-логики, напрямую через Prisma) отклоняется с P2002 —
  проверено отдельным тестом, который делает именно это.
- **Уровень приложения**: 4 прямых решения доступны только из статуса
  `PENDING` — повторное «Подтвердить» на уже `CONFIRMED` достижении
  отклоняется до всякой попытки записи (400 `INVALID_STATUS`).

## 4. Защита от дублей (ТЗ п.2-3)

Два механизма:

- **Предупреждение при создании/отправке** (не блокирует): совпадение
  нормализованного названия + даты + группы + студента у другого
  достижения (не `REJECTED`) → в ответе API `possibleDuplicates`,
  frontend показывает предупреждение и на форме студента, и в карточке
  преподавателя. Достижение не удаляется автоматически — решение
  остаётся за преподавателем (буквально по тексту ТЗ).
- **Жёсткая защита в момент начисления** (это уже не предупреждение):
  если преподаватель подтверждает С БАЛЛОМ запись, у которой есть
  «дубль» (то же название+дата+группа+студент) с уже начисленным
  баллом — решение **блокируется** (409 `DUPLICATE_POINT_BLOCKED`) с
  объяснением, какая запись уже содержит балл. Это прямая реализация
  acceptance-сценария 5 («после подтверждения ОБОИХ записей — не
  допустить двух баллов»): без этой проверки два отдельных Achievement-
  ряда для одного и того же мероприятия дали бы два разных
  `QualificationPoint`, так как уникальный индекс работает на
  `achievementId`, а не на «событие». Это методологическое решение,
  которое ТЗ не расписывает буква в букву — блокировка (а не тихое
  понижение до «без балла») выбрана, чтобы преподаватель осознанно
  разобрался с дублем сам, а не получил незаметно другой результат,
  чем нажал.

## 5. Acceptance-тесты (раздел 38 ТЗ) — все 7 пройдены

`backend/scripts/verify-achievements.ts`, 53 проверки, реальные HTTP-
запросы (включая настоящую multipart-загрузку файла):

1. **Обычный участник** — до проверки 0 баллов; «Подтвердить без
   балла» → `CONFIRMED_NO_POINT`, 0 баллов. ✅
2. **Призовое место** — «Подтвердить» → +1. ✅
3. **Публикация** — «Подтвердить» → +1. ✅
4. **Победитель номинации** — «Подтвердить» → +1. ✅
5. **Дублирование** — предупреждение при создании и при отправке;
   подтверждение первой записи → +1; подтверждение второй (дубль) с
   баллом → заблокировано (409); подтверждение второй без балла →
   разрешено; суммарно у студента — ровно 1 балл, не 2. ✅
6. **Три результата одного мероприятия** — одна запись, один
   `claimedResult` (форма и не позволяет выбрать три одновременно —
   архитектурно исключено), «Подтвердить» → ровно 1 балл. ✅
7. **Пять баллов** — 5 подтверждённых результативных мероприятий →
   Dashboard и Student Profile показывают `oralPartStatus: EXEMPTED`
   («Устная часть: освобождён»). ✅

Плюс общий workflow (черновик → отправка → запрет правки/удаления →
запрос уточнения → правка → повторная отправка → отклонение с
обязательным комментарием), «Изменить статус» с отзывом ошибочно
начисленного балла, права доступа (студент не может решать; чужой
преподаватель получает 404 везде), интеграция с Dashboard (реальные
`kpi.qualificationPoints`, `credit.oralPart`, `achievementsPendingReview`).

Полная регрессия Этапов 1–7 (241 проверка) — без изменений в продукте,
всё зелёное; `verify-dashboard.ts` и `verify-student-profile.ts`
обновлены под новую, теперь честно `implemented: true` форму ответа
(было `implemented: false` до этого этапа — легитимное изменение
контракта, не регрессия).

**Реальный браузер (Playwright/Chromium)** — 47 сценариев (2 сценария):
полный workflow «студент добавляет через 4-шаговую форму (включая
реальную загрузку PDF) → преподаватель находит через «Требуют
проверки» → подтверждает с баллом → студент видит +1 балл → баллы
видны в профиле студента и на Dashboard»; отдельный прогон — сама
вкладчатая структура профиля/Обзора. Мобильная адаптация формы
добавления (375px) — без горизонтального скролла.

### Найденная и исправленная проблема

Шаг «Проверьте данные перед отправкой» не показывал место/номинацию
результата (только тип результата, без деталей) — обнаружено E2E-
тестом (не совпало с ожидаемым текстом на экране), не при чтении кода.
Исправлено: строка «Результат» на экране проверки теперь включает
место/номинацию/уточнение варианта «Другое».

## 6. Портфолио vs квалификационные баллы (ТЗ п.20)

Разделены с самого начала на уровне запроса, не только текста:
портфолио = `count(status IN (CONFIRMED, CONFIRMED_NO_POINT))`,
результативные = `count(status = CONFIRMED)`. Проверено тестом на
студенте с обоими типами подтверждённых достижений.

## 8. Проверка прав доступа

- Студент не может вызвать `PATCH .../decision` (403).
- Студент не видит достижение другого студента напрямую по id (404).
- Чужой преподаватель не видит достижения группы в списке, не может
  открыть карточку, не может вынести решение (404 на всех трёх).
- Без токена — 401.
- Загрузка/просмотр документа — тот же принцип владения, что и у самого
  достижения (не публичный `static`, а защищённый маршрут).

## 9. Мобильный сценарий

Пошаговая форма (Мероприятие → Результат → Подтверждение → Отправить,
ТЗ п.34) — один и тот же компонент на всех размерах экрана (не отдельная
"мобильная" версия формы), реальная загрузка файла через `<input
type="file">` работает и на мобильном viewport. Проверено E2E на 375px:
без горизонтального скролла.

## 10. Что не реализовывалось (осознанно)

- Никаких дополнительных видов/значений баллов, коэффициентов — ровно
  правило «результативное мероприятие = 1 балл» (ТЗ п.36).
- Полный модуль «Зачёт» (допуск по словарю, лексико-грамматический
  тест) — по-прежнему не реализован; из этого этапа в него передан
  ровно один вычисляемый факт (статус устной части), не больше.
- Рейтинги/сортировка студентов по баллам как «лучший/худший» — не
  создавались (ТЗ п.37: «не создавать сложную систему рейтингов»).

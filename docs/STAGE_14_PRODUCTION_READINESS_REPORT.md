## Что проверено

### Production-конфигурация
- Полная инвентаризация переменных окружения: `DATABASE_URL`,
  `JWT_SECRET`, `PORT`, `FRONTEND_ORIGIN`, `COOKIE_SECURE`,
  `EXPOSE_DEV_PASSWORD_RESET_TOKEN` — все 5 переменных, реально
  читаемых кодом (`grep process.env` по всему backend), задокументированы
  в `.env.example`; расхождений нет.
- `JWT_SECRET` не имеет слабого дефолта — приложение отказывается
  стартовать, если секрет не задан явно (проверено чтением
  `utils/jwt.ts`).
- Grep по всему frontend на `api[_-]?key|secret|Bearer <токен>|sk_live|
  sk_test` — **0 совпадений**: ни одного захардкоженного секрета или
  API-ключа в клиентском коде. Единственная переменная окружения,
  используемая на frontend — `VITE_API_URL` (публичный адрес backend,
  не секрет).
- Обработка ошибок: единый backend error-handler отдаёт только
  `{error, message}` на русском, стектрейс никогда не попадает в ответ
  клиенту (подтверждено чтением `index.ts` — не изменилось с Этапа 11).

### База данных
- **Индексы** — прямой запрос к `sqlite_master` работающей БД показал
  **36 явных `@@index`** (не считая автоматических PK/unique) —
  ровно на тех полях, которые перечислило задание: поиск группы
  (`GroupJoinCode.code` — unique, `Group.teacherId`/`Group.courseId`),
  membership (`GroupMembership.studentId`, `.groupId`, оба по
  отдельности плюс уникальная составная пара), student profile
  (`StudentProfile.userId`), teacher dashboard (`Course.teacherId`/
  `.academicYearId`, вся цепочка выше), диагностика
  (`DiagnosticAttempt.studentId`/`.groupId`, `DiagnosticAnswer.
  attemptId`), достижения (`Achievement.groupId`/`.studentId`/
  `.status`, `QualificationPoint.studentId+groupId`). Индексы
  добавлялись по мере реализации каждого этапа — на момент Этапа 14
  пробелов не найдено, новых индексов добавлять не потребовалось.
- **Foreign keys** — каждая связь в `schema.prisma` объявлена с
  `onDelete: Cascade`; ни одна модель не хранит "осиротевшую" ссылку.
- **Unique constraints** — весь критичный для целостности набор
  подтверждён (не создаёт дубль membership/попытки диагностики или
  анкеты/квалификационного балла/попытки зачётного теста/записи
  устной части) — та же проверка, что и в Этапе 11/12, регрессии нет.
- **RLS/security policies** — приложение не использует Supabase;
  эквивалент — серверная проверка владения на каждом маршруте
  (`requireAuth`/`requireRole` + прямой `WHERE teacherId/studentId =
  req.user.id`). Точечно перепроверено чтение всех "сырых"
  `findUnique`/`findFirstOrThrow` вызовов по всем файлам маршрутов —
  каждый либо самообращение по `req.user.id`, либо использует id,
  уже провалидированный предыдущим owner-scoped запросом в той же
  функции. Ни одного случая доверия параметру URL "как есть".
- **Orphan records** — во всём backend всего 3 маршрута `DELETE`
  (черновик своего достижения, файл доказательства, файл заявки на
  допуск), ни один не удаляет родительскую сущность — риска
  осиротевших связей нет структурно.

Полная матрица Teacher A → Group B, Student A → Student B, подмена id

(**444 проверки**) плюс `verify-qa-audit-security.ts` (IDOR на
attempt-id, попытки подмены сервер-вычисляемых полей) прогнана заново
после всех правок этого этапа — **0 регрессий**.

### Data Privacy
Живая проверка (не только по коду): свежезарегистрированный Teacher B
видит пустой список групп, не видит ни одной сущности Teacher A;
собственный профиль возвращает ровно то, что относится к текущему
пользователю. Совпадает с постоянно подтверждаемым во всех `verify:*`
инвариантом «чужая сущность — 404, не утечка через 200 с частичными
данными».

## Что исправлено

1. **`npm start` был сломан** (не связано с функционалом — чисто
   конфигурация сборки). `package.json`: `"start": "node dist/
   index.js"` — но `tsc -p .` реально кладёт скомпилированный вход в
   `dist/src/index.js` (`rootDir` схватывает `backend/`, а не
   `backend/src/`, потому что `scripts/` тоже входит в `include` для
   типизации verify/pilot-скриптов). Раньше это не было замечено ни на
   одном этапе, потому что вся разработка и тестирование шли через
   `npm run dev` (`tsx watch`), а не через реальную production-сборку.
   Обнаружено и исправлено именно на этом этапе, специально
   посвящённом финальной сборке — `start` теперь указывает на
   `dist/src/index.js`, проверено живым запуском скомпилированного
   сервера с реальным обращением к БД. Альтернатива (сузить `rootDir`/
   `include` до одного `src`) была рассмотрена и отклонена — она
   тихо убрала бы typecheck-покрытие `scripts/*.ts` из `npm run
   build`, которым несколько предыдущих этапов ловили реальные ошибки
   в verify/pilot-скриптах.

Больше исправлений не потребовалось — все остальные проверки этого
этапа (индексы, security, приватность, производительность, мобильный
UX, визуальная согласованность, язык, изоляция тестовых данных)
подтвердили уже существующее корректное поведение без находок,
требующих правки.

## Что осталось (ограничения, известны с предыдущих этапов, без
изменений)

- SQLite — провайдер в `schema.prisma` захардкожен (`provider =
  "sqlite"`), не читается из окружения. Переход на Postgres для
  реального production-масштаба потребует правки схемы и повторной
  миграции, не только смены `DATABASE_URL`.
- Таблица студентов Dashboard без серверной пагинации — не рассчитана
  на очень крупные группы (сотни-тысяча студентов), для реалистичного
  размера учебной группы (15–35 человек) не является проблемой.
- Изменение курсовых настроек зачёта (лимит попыток/показ ответов) не
  пишется в `CreditAuditLog` — все per-student решения полностью
  покрыты историей, только эта курсовая настройка нет.
- 4 честные заглушки «в разработке» (Студенты/Аналитика/Настройки у
  преподавателя, Мои цели у студента) — архитектурно предусмотрены,
  не реализованы; убирать их не входило в задачу этого этапа («не
  добавляй новые функции»).

## Что необходимо сделать перед публикацией

1. **Подключить реальный email-провайдер для восстановления пароля**
   (единственный пункт, отделяющий от безусловного «Ready»). Сейчас
   `EXPOSE_DEV_PASSWORD_RESET_TOKEN` по умолчанию выключен (это
   правильно и безопасно — без него токен нигде не светится), но это
   означает, что реальный пользователь, забывший пароль, физически не
   получит письмо со ссылкой восстановления. Нужно интегрировать
   любой email-провайдер (SendGrid/Postmark/SMTP и т.п.) в
   `POST /api/auth/forgot-password` и убедиться, что
   `EXPOSE_DEV_PASSWORD_RESET_TOKEN` не установлен в продакшн-
   окружении.
2. Заполнить реальные значения `.env` перед деплоем: сгенерировать
   длинный случайный `JWT_SECRET` (не `dev-only-secret-change-me`),
   `COOKIE_SECURE=true` (HTTPS), `FRONTEND_ORIGIN` — реальный домен,
   `EXPOSE_DEV_PASSWORD_RESET_TOKEN` — не установлен/`false`.
3. Решить вопрос СУБД для реального масштаба — либо сознательно
   остаться на SQLite (подходит для пилота/небольшого числа
   одновременных пользователей), либо заранее подготовить переход на
   Postgres (правка `schema.prisma` + миграция) до роста нагрузки.
4. Перед запуском с реальными преподавателями и студентами — удалить
   пилотный тестовый набор Этапа 13 (`DELETE FROM "User" WHERE email
   LIKE '%@pilot.test'`, каскад в схеме сам подчистит связанные
   записи) либо явно согласовать, что он остаётся как демо-набор
   (изоляция по домену `.test` делает оба варианта безопасными).
5. Запустить `npm run build` на реальном сервере деплоя (не только
   локально) и убедиться, что `npm start` поднимается — процесс теперь
   исправен и проверен, но стоит подтвердить ещё раз именно в целевой
   среде развёртывания (другая ОС/версия Node и т.п. могут повести
   себя иначе, хотя код кроссплатформенный).

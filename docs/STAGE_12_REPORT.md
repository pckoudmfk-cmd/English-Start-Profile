# Этап 12. СТАБИЛИЗАЦИЯ ПРИЛОЖЕНИЯ — отчёт

Приложение переведено из режима поэтапной разработки в режим
подготовки к использованию. **Новая функциональность не добавлялась**,
методическая логика, структура зачёта и правила квалификационных
баллов **не менялись** — только исправление, регрессия и уборка.

## 1. Исправленные ошибки

### CRITICAL (перенесён из `docs/STAGE_11_QA_REPORT.md`)

**Токен восстановления пароля возвращался в API-ответе безусловно** —
`backend/src/routes/auth.ts`, `POST /api/auth/forgot-password`. Раньше
`devToken` попадал в JSON-ответ и в лог сервера всегда, независимо от
окружения — путь к полному захвату любого аккаунта (включая
преподавательский) по одному известному email, без доступа к почте.

**Исправлено**: добавлен явный opt-in флаг
`EXPOSE_DEV_PASSWORD_RESET_TOKEN` (по умолчанию выключен/не
установлен — токен нигде не появляется). Установлен `true` только в
локальном `backend/.env` (не в git — `.gitignore`) для тестирования без
email-провайдера; `.env.example` явно предупреждает не включать в
проде. Осознанно выбран **безопасный по умолчанию** дизайн (а не
`NODE_ENV !== "production"`) — частая причина именно таких утечек:
забытая переменная окружения не деплое включает опасное поведение по
умолчанию, а не выключает его.

**Проверено вживую в обе стороны** (не только чтением кода): отдельный
временный процесс backend с `EXPOSE_DEV_PASSWORD_RESET_TOKEN=false`
подтвердил — токен отсутствует в ответе; основной dev-процесс с флагом
`true` — токен присутствует, как и ожидается для разработки.

### LOW (из Этапа 11)

Общий 404-обработчик несуществующих API-маршрутов не содержал
`message` — добавлен русский текст (см. `STAGE_11_QA_REPORT.md`).

## 2. Новое регрессионное покрытие (пробел, обнаруженный при аудите)

У узла восстановления доступа (`forgot-password`/`reset-password`)
**не было вообще никакой автоматической проверки** — при этом именно
там был найден Critical. Написан `backend/scripts/verify-password-
reset.ts` (**14 проверок**): полный цикл (получить токен → сбросить
пароль → войти новым паролем), невалидный токен, истёкший токен
(эмуляция через прямую правку `passwordResetExpiresAt` в БД),
одноразовость токена (повторное использование отклоняется), нейтральное
сообщение не палит факт регистрации email, короткий пароль отклонён,
и — отдельно — сама проверка исправления Critical (при выключенном
флаге `devToken` действительно отсутствует).

## 4. Целостность данных (п.2 задания)

Ре-верификация (код + `verify:*`): ни один результат не теряется,
исторические диагностики не перезаписываются (`kind="START"` заморожен,
`kind="PROGRESS"` — отдельная строка), повторная попытка — всегда новая
запись (`@@unique([studentId, groupId, kind])` на уровне БД), достижение
не создаёт дублирующий балл (`QualificationPoint.achievementId
@unique` + защита в момент подтверждения через `DUPLICATE_POINT_
BLOCKED`), одно мероприятие не может дать больше 1 балла — подтверждено
и на уровне БД, и в бизнес-логике.

**"Удаление membership не уничтожает исторические результаты"** —
отдельно проверено структурно: в приложении **нет** ни одного маршрута
удаления `GroupMembership` (нельзя "исключить студента из группы" —
такой функциональности не существует ни на одном этапе). Это не
пробел этого аудита — специально проверено, что если бы такая
функция появилась, она была бы безопасна по конструкции схемы: ни
`DiagnosticAttempt`, ни `QuestionnaireAttempt`, ни `Achievement`, ни
`CreditTestAttempt`/`OralAssessment` не ссылаются на `GroupMembership.
id` — все они хранят `studentId`+`groupId` напрямую на `User`/`Group`,
поэтому удаление строки членства физически не может каскадно стереть
исторические результаты.

Полная матрица Teacher A → Group A / Teacher B → Group B / Student A →
Group A / Student B → Group B повторно подтверждена всей линейкой
`verify:*` (415 предыдущих + 15 из `verify-qa-audit-security.ts`) —
без единой регрессии после исправления Critical. Прямой доступ через
URL и напрямую к backend (не только по интерфейсу) — везде 404 на

## 6. Формы (п.4 задания)

Точечная проверка вживую (не только по коду): пустое название учебного
года/курса/группы — `VALIDATION_ERROR` с понятным русским
`fieldErrors`; регистрация со слабым паролем/некорректным email —
отклонена с понятным сообщением. Проверено, что форма создания группы
физически не может дойти до пустого `courseId` через интерфейс —
если курсов нет, форма вообще не рендерится, вместо неё честный
`EmptyState` со ссылкой "Сначала создайте курс" (`GroupsPage.tsx`).
Анкета — автосохранение, `PUT .../answers` идемпотентен, повторное
открытие резюмирует прогресс, завершённая анкета неизменяема (`409
ATTEMPT_COMPLETED`) — то же самое, что проверялось на Этапе 4/11,
подтверждено без регрессии.

## 10. Производительность (п.8 задания)

Dashboard и профиль студента **не** загружают весь объём анкеты/всю
историю диагностики при открытии — подтверждено чтением кода:
`analytics/teacherAccess.ts` (`buildMetricsForRoster`) выбирает только
`DASHBOARD_QUESTION_CODES` (узкий подмножество полей анкеты, не все
45 вопросов) одним батч-запросом `WHERE questionCode IN (...)` без
N+1; `TeacherStudentProfilePage.tsx` подгружает полную анкету и полную
историю диагностики **лениво**, только при открытии соответствующей
вкладки (`activeTab === "questionnaire" && !questionnaire`), не при
заходе на страницу профиля. Ограничение по масштабу (пагинация
таблицы студентов при очень больших группах) остаётся открытым —
см. раздел «Ограничения» ниже, как и в Этапе 11.

## 11. Технический мусор (п.9 задания)

Целевой аудит на неиспользуемые файлы/компоненты, `console.log/debug/
warn` (кроме двух легитимных: старт сервера и уже-загейченный dev-лог
восстановления доступа), `TODO/FIXME/XXX/HACK`, `lorem ipsum`,
демо/тестовые кнопки, фиктивные production-значения — **ничего не
найдено** ни во frontend, ни в backend. Все `.tsx`/`.ts`-файлы
реально используются (проверено скриптом сопоставления импортов —
единственное "неиспользуемое" совпадение, `vite-env.d.ts`, это
штатный ambient-файл типов Vite, не мёртвый код). Seed/demo-скрипта в
репозитории нет вообще — отделять нечего.

Четыре заглушки `InDevelopment` (`/teacher/students`, `/teacher/
analytics`, `/teacher/settings`, `/student/goals`) **сознательно
оставлены без изменений** — это не случайный мусор, а честно
промаркированные нереализованные разделы («Раздел находится в
разработке… появится на одном из следующих этапов»), убирать их
означало бы либо ломать существующую навигацию, либо тихо
скрывать факт незавершённости — оба варианта хуже честной заглушки.
Добавление реального содержимого сюда — новая функциональность,
прямо запрещённая заданием этого этапа.

## Какие ограничения остались (без изменений с Этапа 11 — не в

## Готово ли приложение к ручному пользовательскому тестированию

**Да.** Единственная причина прошлой оценки NOT READY (Этап 11,
утечка токена восстановления пароля) устранена и подтверждена прямой
проверкой в обе стороны, плюс покрыта регрессией. Полная линейка
проверок (444 backend-скрипта + непрерывный мобильный E2E) зелёная,
production-сборка чистая на обеих сторонах, технического мусора не
найдено. Оставшиеся ограничения — операционные (масштаб на очень
большую группу, переход на Postgres) и продуктовые честные заглушки,
ни одно не блокирует ручное пользовательское тестирование с реальными
преподавателями и студентами в рамках пилота обычного размера
(несколько групп по 15–35 человек).

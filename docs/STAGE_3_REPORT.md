# Этап 3. Подключение студента к группе — отчёт

Статус: **реализовано и проверено**. Progress Check и Credit Test не
открывались — как и требовалось. Анкетирование и Start Diagnostic тоже
не реализовывались.

## 1. Модель данных

Добавлена модель `GroupMembership` (`backend/prisma/schema.prisma`):

- `studentId` + `groupId`, уникальны в паре — гарантия «не создавать
  дубликат membership» на уровне БД, а не только в коде;
- `status` (`ACTIVE` / `REMOVED`) — сейчас всегда `ACTIVE`; поле
  добавлено заранее для будущего удаления студента из группы
  преподавателем (soft-delete), которое ещё не реализовано;
- `joinedViaCode` — снимок кода на момент присоединения (не ссылка на
  текущий `GroupJoinCode`, который мог быть потом регенерирован);
- `joinedAt` / `removedAt`.

Также добавлено поле `GroupJoinCode.expiresAt` (nullable, по умолчанию
`null` = бессрочно) — без него нельзя было бы честно проверить и
показать сценарий «код просрочен» из ТЗ. Интерфейс для установки срока
преподавателем пока не создавался (это отдельная задача одного из
следующих этапов), но серверная проверка и сообщение об истёкшем коде
уже работают.

## 2. Сценарий подключения (как реализовано)

1. Студент видит на главной странице карточку «Присоединиться к
   группе» с полем «Введите код группы».
2. После ввода корректного кода — превью: название группы, курс,
   учебный год, преподаватель (ФИО из профиля преподавателя, либо
   email, если профиль не заполнен).
3. Кнопка «Подтвердить присоединение» создаёт `GroupMembership`.
4. После подключения группа сразу появляется в разделе «Мои группы» на
   главной странице студента со статусом **«Стартовая диагностика: не
   пройдена»**.

Код нормализуется на backend (обрезка пробелов, верхний регистр) — не
важно, как студент его наберёт.

## 3. Ошибки — с чёткими различиями

| Ситуация | HTTP | Код ошибки | Сообщение студенту |
|---|---|---|---|
| Кода не существует / опечатка | 404 | `CODE_NOT_FOUND` | «Код не найден. Проверьте правильность ввода.» |
| Код отключён преподавателем | 410 | `CODE_DISABLED` | «Этот код подключения отключён преподавателем.» |
| Срок действия кода истёк | 410 | `CODE_EXPIRED` | «Срок действия этого кода истёк. Обратитесь к преподавателю за новым кодом.» |

«Неверный» и «не существует» из ТЗ объединены в один и тот же случай
(`CODE_NOT_FOUND`) — с точки зрения системы придуманный код и опечатка
неотличимы друг от друга, разводить их искусственно означало бы
показывать несуществующее различие.

## 4. Повторное подключение

Если студент уже состоит в группе — и на этапе превью, и на этапе
подтверждения — интерфейс показывает **«Вы уже состоите в этой
группе.»**, кнопка подтверждения не показывается на превью, а сам
запрос на присоединение идемпотентен: повторный `POST …/join` не
создаёт вторую запись `GroupMembership` (проверено прямым подсчётом
строк в БД в скрипте проверки, не только по ответу API).

## 5. Побочное исправление, перенесённое из Этапа 2

При архивировании группы её активный join-код теперь автоматически
деактивируется (раньше — нет, это было зафиксировано как открытый
вопрос в отчёте по Этапу 2). Без этого исправления можно было бы
присоединиться к архивной группе, если её код случайно остался
активным. Также заблокирована регенерация кода архивной группы
(`409 GROUP_ARCHIVED`) — управлять кодом можно только после
восстановления группы из архива.

## 6. Что НЕ реализовано (сознательно)

- Progress Check и Credit Test — не создавались.
- Анкетирование, Start Diagnostic — не создавались.
- Удаление студента преподавателем из группы (`status: REMOVED`) —
  поле в схеме есть, эндпоинта нет.
- Установка `expiresAt` через интерфейс преподавателя — колонка есть,
  UI нет.

## 7. Протестированные сценарии

**Backend, `backend/scripts/verify-student-onboarding.ts`** (29/29
пройдено), реальные HTTP-запросы к работающему серверу:

1. Превью корректного кода — группа, курс, учебный год и имя
   преподавателя совпадают с реально созданными.
2. Код нечувствителен к регистру и пробелам по краям.
3. Подтверждение присоединения создаёт ровно одну запись
   `GroupMembership` (проверено прямым запросом к БД через Prisma, не
   только по ответу API).
4. Повторное присоединение по тому же коду: `200`, сообщение «Вы уже
   состоите в этой группе.», **не** создаёт вторую запись
   `GroupMembership` (снова проверено подсчётом строк в БД).
5. Несуществующий код → `404 CODE_NOT_FOUND`.
6. Код, отключённый преподавателем (`join-code/deactivate`) → `410
   CODE_DISABLED`.
7. Просроченный код (`expiresAt` в прошлом, выставлено напрямую через
   Prisma для теста) → `410 CODE_EXPIRED`, сообщение отличается от
   сообщения для отключённого кода.
8. Код архивной группы → `410 CODE_DISABLED` (автоматическая
   деактивация при архивировании).
9. Попытка присоединиться по нерабочему коду не создаёт
   `GroupMembership` (подсчёт строк в БД = 0).
10. Список групп студента (`GET /api/student/groups`) содержит только
    его собственные группы: Student A не видит группу Student B и
    наоборот (оба присоединились к разным группам разных
    преподавателей) — изоляция, аналогичная Этапам 1–2.
11. Список содержит `startDiagnosticStatus: "NOT_STARTED"` для каждой
    группы.
12. Без токена `/api/student/groups` → `401`; с ролью `TEACHER` вызов
    `/api/student/groups/join` → `403`.

**Реальный браузер (Playwright/Chromium), полный сценарий через
настоящий UI**, без единого прямого вызова API из теста:

1. Преподаватель регистрируется, заполняет ФИО, создаёт учебный год →
   курс → группу → получает код на странице группы.
2. Студент регистрируется, на главной странице вводит заведомо неверный
   код — видит «Код не найден. Проверьте правильность ввода.».
3. Вводит настоящий код — видит превью с названием группы, курсом,
   учебным годом и именно тем ФИО преподавателя, которое было указано в
   его профиле.
4. Нажимает «Подтвердить присоединение» — видит сообщение об успехе.
5. На главной странице появляется карточка группы со статусом
   «Стартовая диагностика: не пройдена».
6. Повторно вводит тот же код — интерфейс показывает «Вы уже состоите
   в этой группе.» (не ошибку, не дубликат).

Оба скрипта воспроизводимы: `npm run verify:onboarding` в `backend/`
для API-уровня; браузерный сценарий прогнан вручную при разработке
этапа (как и в Этапах 1–2).

**Побочно перепроверены и остались зелёными** (без регрессий):
`npm run verify:access` (11/11, Этап 1) и `npm run verify:workspace`
(23/23, Этап 2).

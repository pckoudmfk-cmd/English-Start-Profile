# Этап 2. Курсы, группы и код подключения — отчёт

Статус: **реализовано и проверено**. Анкетирование и диагностика не
затрагивались. Student Onboarding (присоединение студента по коду) на
этом этапе намеренно **не реализован** — по прямому указанию в ТЗ.
Членства студентов (`GroupMembership`) в схеме БД пока нет вообще —
модель для него будет спроектирована на следующем этапе, вместе с
самим onboarding'ом, а не заранее вслепую.

## 1. Teacher Workspace

Иерархия: `AcademicYear` → `Course` → `Group`, каждая модель хранит
`teacherId` напрямую (а не только через цепочку связей) — защита в
глубину при проверке владения.

Реализовано:

- создание учебного года (`/teacher/academic-years`);
- создание курса/дисциплины с привязкой к учебному году
  (`/teacher/courses`);
- создание группы с привязкой к курсу, специальностью
  (`/teacher/groups`);
- открытие группы (`/teacher/groups/:id`);
- редактирование названия группы;
- архивирование / восстановление из архива.

Пример из ТЗ воспроизводится один в один: учебный год «2026–2027» →
курс «Английский язык» → группа «1ФИН-24» → специальность «Финансы».

## 2. Join Code

Каждая группа при создании автоматически получает код вида
`ENG-7K4P9` (`backend/src/utils/joinCode.ts`):

- алфавит без визуально неоднозначных символов (без `0/O`, `1/I/L`);
- код — случайная строка, генерируется и хранится отдельно от `id`
  группы; по коду нельзя вычислить id и наоборот (проверено в скрипте
  проверки, см. ниже);
- уникальность обеспечена `@unique` в БД + повторной генерацией при
  коллизии;
- код хранится в отдельной таблице `GroupJoinCode`, привязан к
  `groupId`, а не к преподавателю — что и требовалось.

Действия: **показать** (на странице группы), **скопировать** (через
`navigator.clipboard`), **регенерировать** (старый код помечается
`active=false, revokedAt=now()`, создаётся новый — история кодов не
удаляется), **деактивировать** (группа остаётся без активного кода,
пока преподаватель не регенерирует новый).

## 3. Ограничения — как учтены в архитектуре

- Модель `Group` рассчитана на множественное членство «многие ко
  многим» через будущую таблицу `GroupMembership` (не создана в этом
  этапе) — один студент сможет состоять в нескольких группах.
- `GroupJoinCode` никогда не удаляется — только `active=false`, чтобы
  при появлении членства не терять историю подключений по коду.
- Поскольку членства в этом этапе нет, вопрос «не удалять исторические
  результаты при удалении из группы» и «не показывать студенту данные
  других групп» напрямую не тестировался (нечего тестировать до
  Student Onboarding) — но учтён как ограничение архитектуры на
  следующий этап (см. раздел «Открытые вопросы» ниже).

## 4. Интерфейс

Русскоязычные разделы преподавателя дополнены: **Учебные годы**,
**Курсы**, **Группы** (полностью функциональны). «Студенты» и
«Настройки» остаются заглушкой «в разработке» — как и было решено не
переходить к Student Onboarding. Никаких декоративных изображений;
только карточки, списки и статус-бейджи (Активна/Архив, код).

## 5. Проверка

**Backend, скрипт `backend/scripts/verify-workspace-isolation.ts`**
(23/23 пройдено) — воспроизводит сценарий из ТЗ дословно:

```
Teacher A → Course A → Group A → Code A
Teacher B → Course B → Group B → Code B
```

и проверяет:

- Group A и Group B получают разные join-коды, код не содержит id
  группы;
- список учебных годов/курсов/групп Teacher A не содержит сущности
  Teacher B (и наоборот);
- прямой запрос по id чужой группы, чужого курса, чужого учебного
  года → `404` (не `403`, чтобы не подтверждать факт существования
  чужого ресурса);
- нельзя создать курс в чужом учебном году, группу в чужом курсе,
  переименовать/архивировать/регенерировать код чужой группы — все
  попытки → `404`;
- регенерация и деактивация кода корректно работают на своей группе;
- защищённые маршруты недоступны без токена (`401`).

**Реальный браузер (Playwright/Chromium)** — тот же сценарий, но через
настоящий UI, не через прямые API-вызовы: Teacher A и Teacher B
регистрируются, каждый создаёт год → курс → группу → получает код
через интерфейс; после этого:

- Teacher A не видит группу B в своём списке групп;
- Teacher A не видит учебный год B в своём списке;
- прямой переход Teacher A по URL страницы группы B показывает
  «Группа не найдена» (не содержимое чужой группы).

Оба скрипта воспроизводимы: `npm run verify:workspace` в `backend/`
для API-уровня; браузерный сценарий прогнан вручную при разработке
(как и в Этапе 1, не закреплён в репозитории как CI-таск — кандидат на
закрепление в общем E2E-покрытии позже).

## 6. Открытые вопросы к следующему этапу (Student Onboarding)

- **Модель членства.** Нужно спроектировать `GroupMembership`
  (studentId, groupId, статус ACTIVE/REMOVED, joinedAt, removedAt) с
  учётом: один студент — несколько групп; удаление из группы — мягкое
  (soft-delete), без удаления исторических данных; повторное
  присоединение по тому же коду после удаления — отдельный вопрос,
  требующий решения (разрешить или нет).
- **Валидация кода при вступлении.** Нужен публичный (для
  аутентифицированного студента) эндпоинт вида
  `POST /api/student/groups/join` с кодом в теле — код должен
  находиться регистронезависимо/с обрезкой пробелов, отдавать понятную
  ошибку на неактивный/несуществующий код, и не путать «неверный код»
  с «код принадлежит архивной группе» (это разные ситуации).
- **Присоединение к архивной группе.** Сейчас архивирование группы не
  трогает её join-код автоматически — при переходе к Student
  Onboarding нужно решить: архивирование должно ли автоматически
  деактивировать код (иначе можно присоединиться к архивной группе).
  Рекомендация: деактивировать код при архивировании и не позволять
  регенерировать код для архивной группы, пока она не восстановлена.
- **Показ студентов преподавателю.** Раздел «Студенты» в навигации
  преподавателя остаётся плейсхолдером — после появления членства его
  нужно наполнить реальным списком по группе, без фиктивных данных.

Автоматически к Student Onboarding не переходим — ждём подтверждения.

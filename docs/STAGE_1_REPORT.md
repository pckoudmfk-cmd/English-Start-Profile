# Этап 1. Авторизация, роли и профили пользователей — отчёт

Статус: **реализовано и проверено**. Анкетирование, тесты, достижения,
зачёт и аналитика группы на этом этапе не реализовывались — согласно
техническому заданию.

## 1. Таблицы / модели

СУБД: SQLite (разработка), схема совместима с переходом на Postgres в
проде (Prisma). Файл схемы: `backend/prisma/schema.prisma`.

| Модель | Назначение | Ключевые поля |
|---|---|---|
| `User` | учётная запись, аутентификация | `id`, `email` (unique), `passwordHash`, `role`, `passwordResetTokenHash`, `passwordResetExpiresAt` |
| `TeacherProfile` | профиль преподавателя, 1:1 с `User` | `userId` (unique), `fullName`, `organization`, `department`, `position`, `workEmail` |
| `StudentProfile` | профиль студента, 1:1 с `User` | `userId` (unique), `fullName`, `email`, `specialty`, `course`, `academicYear` |

Роль хранится строкой (`TEACHER` / `STUDENT` / `ADMIN`), а не нативным
enum БД — осознанное решение, чтобы схема одинаково работала на SQLite
и Postgres без миграции типа при переезде. Валидация значения — на
уровне приложения (`backend/src/utils/roles.ts`).

## 2. Реализованные роли

- **Преподаватель (`TEACHER`)** — регистрация, вход, профиль.
- **Студент (`STUDENT`)** — регистрация, вход, профиль.
- **Администратор (`ADMIN`)** — предусмотрен в архитектуре (значение
  роли, схема БД, точка расширения в `requireRole`), но публичная
  регистрация с этой ролью закрыта: `POST /api/auth/register`
  принимает только `TEACHER` и `STUDENT` (см. `SELF_REGISTERABLE_ROLES`
  в `backend/src/utils/roles.ts`). Административной панели, как и
  требовалось, нет.

## 3. Реализованные правила доступа

Ключевой принцип: **разграничение реализовано на backend, а не только
скрытием пунктов меню**.

- Каждый защищённый маршрут API требует валидный JWT в httpOnly-cookie
  (`requireAuth`) и, где нужно, конкретную роль (`requireRole`).
- Владелец ресурса определяется **исключительно** по `req.user.id` из
  проверенного токена. Маршруты профиля не принимают `:id` в URL — то
  есть нет ни одного эндпоинта, где чужой профиль можно запросить,
  подставив другой идентификатор.
- Студент, вызывающий преподавательский эндпоинт (и наоборот),
  получает `403 FORBIDDEN` независимо от того, что показывает
  интерфейс.
- Восстановление пароля не раскрывает, зарегистрирован ли email в
  системе (одинаковый ответ для существующего и несуществующего
  адреса) — защита от перебора адресов.
- Пароли хранятся только как bcrypt-хэш; токен восстановления доступа
  — только как sha256-хэш, срок жизни 1 час, одноразовое использование.

На фронтенде дополнительно есть `RoleRoute` — редиректит студента при
попытке открыть `/teacher/*` (и наоборот) обратно в его раздел. Это
**UX-удобство, а не граница безопасности**; она явно закомментирована
как таковая в `frontend/src/routes/RoleRoute.tsx`, чтобы на будущих
этапах не возникло иллюзии, что фронтенд что-то защищает сам по себе.

## 4. Защищённые маршруты

**API (backend):**

| Маршрут | Метод | Требования |
|---|---|---|
| `/api/auth/register` | POST | публичный |
| `/api/auth/login` | POST | публичный |
| `/api/auth/logout` | POST | публичный |
| `/api/auth/me` | GET | аутентификация |
| `/api/auth/forgot-password` | POST | публичный |
| `/api/auth/reset-password` | POST | публичный (по токену) |
| `/api/teacher/profile` | GET/PUT | аутентификация + роль `TEACHER` |
| `/api/student/profile` | GET/PUT | аутентификация + роль `STUDENT` |

**Frontend (маршрутизация):**

| Путь | Требования |
|---|---|
| `/teacher/*` | роль `TEACHER`, иначе редирект на `/login` или в свой раздел |
| `/student/*` | роль `STUDENT`, иначе редирект на `/login` или в свой раздел |
| `/login`, `/register`, `/forgot-password`, `/reset-password` | публичные |

## 5. Выполненные проверки

Все проверки — по реальным HTTP/браузерным сценариям, без моков и без
фиктивных данных для заполнения интерфейса.

**Backend, скрипт `backend/scripts/verify-access-control.ts`**
(11/11 пройдено): создаёт Teacher A, Teacher B, Student A, Student B
через настоящий `/api/auth/register`, заполняет их профили разными
данными и проверяет:

- Сценарий A/B — Teacher A получает только свой профиль, Teacher B —
  только свой; ответы для A и B различаются.
- Сценарий C/D — то же для Student A / Student B.
- Прямой доступ по URL — вызов `/api/teacher/profile` от имени
  студента → `403`; вызов `/api/student/profile` от имени
  преподавателя → `403`.
- Без токена — оба маршрута → `401`.
- Подмена cookie на cookie другого пользователя возвращает данные
  именно этого (другого) пользователя, а не исходного — то есть
  авторизация действительно завязана на сессию, а не на что-то в теле
  запроса.

**Браузер (Playwright, headless Chromium), реальный UI, не curl:**

- Студент регистрируется через форму → попадает на `/student`.
- Прямой переход в адресной строке на `/teacher` → отброшен на
  `/student` (Teacher Dashboard не показан).
- Прямой переход на `/teacher/profile` → тот же результат.
- `fetch('/api/teacher/profile', {credentials:'include'})`,
  выполненный из консоли/страницы этой же аутентифицированной сессии
  студента, → `403` (backend реально проверяет роль, а не просто
  фронтенд не даёт кликнуть).
- Анонимный контекст без cookie → переход на `/teacher` отправляет на
  `/login`.

Обе проверки воспроизводимы: `npm run verify:access` в `backend/` (для
браузерного сценария скрипт не входит в репозиторий как постоянный
таск раннера — он был выполнен вручную при разработке этапа; при
необходимости регрессионного E2E-покрытия его стоит закрепить в CI на
следующих этапах).

## 6. Архитектурные вопросы к следующему этапу

- **Cookie в проде.** Сейчас `SameSite=Lax`, что корректно работает,
  пока frontend и backend на одном registrable domain (в т.ч. разные
  порты на `localhost`, как в разработке). Если в проде они окажутся
  на разных доменах (например, `app.example.com` и `api.example.com`),
  потребуется `SameSite=None; Secure` и повторная проверка CSRF-рисков
  для PUT/POST-запросов. Лучше сразу выбрать топологию (единый домен
  через reverse proxy — предпочтительно) до деплоя.
- **Отправка email не подключена.** `forgot-password` реализован
  полностью на backend (токен, срок жизни, одноразовость), но вместо
  письма токен возвращается в ответе API и пишется в лог — это явно
  промаркировано как dev-режим в коде. Перед реальной эксплуатацией
  нужен почтовый провайдер.
  и токен нужно убрать из ответа API.
- **Нет rate limiting** на `/api/auth/login` и `/api/auth/register` —
  стоит добавить до публичного открытия доступа (защита от подбора
  пароля и спама регистраций).
- **Отзыв токена.** JWT стателесс, живёт 7 дней; logout лишь удаляет
  cookie на клиенте — если токен скомпрометирован, он остаётся
  действителен до истечения срока. Пока цена этого невысока (нет
  чувствительных данных), но к этапу с зачётом и баллами стоит
  предусмотреть механизм отзыва (например, версия сессии в БД).
- **Создание администратора.** Роль есть в схеме, но ни один маршрут
  её не выдаёт — на данный момент администратора можно завести только
  прямой записью в БД. Это осознанно (по ТЗ), но нужен вопрос: когда и
  как появится первый администратор (сид-скрипт? отдельный
  защищённый маршрут с одноразовым ключом?).
- **Многотенантная модель следующего этапа.** Согласно полной
  спецификации (`docs/SPEC.md`, разделы 58–61), учебные группы и
  join-коды принципиально многотенантны: один студент может состоять
  в нескольких группах у разных преподавателей, и данные по каждой
  группе должны быть изолированы отдельно от глобального профиля
  студента. Текущая схема (`User` → `TeacherProfile` /
  `StudentProfile`) к этому готова (не создаёт противоречий), но
  `Group`, `CourseEnrollment` и связанные модели ещё не спроектированы
  — их стоит закладывать с учётом этой изоляции с самого начала
  следующего этапа, а не как надстройку поверх плоской модели.

Автоматически к следующему этапу не переходим — ждём подтверждения.

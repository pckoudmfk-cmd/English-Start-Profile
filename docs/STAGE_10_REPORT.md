# Этап 10. ПРОМЕЖУТОЧНАЯ ДИАГНОСТИКА (PROGRESS CHECK) — отчёт

Статус: **реализовано и проверено**. Отдельный от Start Diagnostic
(Этап 5) снимок прогресса — Start Diagnostic никогда не перезаписывается,
каждая диагностика (Start/Progress) хранится как отдельная попытка.

## 1. Какие сущности созданы/изменены

`backend/prisma/schema.prisma`:

- **`DiagnosticAttempt`/`QuestionnaireAttempt`** — активировано ранее
  зарезервированное (с Этапа 4/5) значение `kind = "PROGRESS"`
  (`kind = "CREDIT"` на Этапе 9 намеренно осталось дремлющим — там было
  прямо противоположное решение: полная изоляция моделей). Добавлены
  поля назначения: `assignedByTeacherId`, `assignedAt`, `periodStartAt`,
  `periodEndAt`; новое значение статуса `"ASSIGNED"` (до этого — только
  `IN_PROGRESS`/`COMPLETED`).
- **Form B** (`backend/src/diagnostic/itemBankB.ts`) — 32 новых задания
  (12 Grammar / 10 Vocabulary / 6 Reading / 4 Listening), тот же состав
  навыков/сложности/распределения, что и у Form A, но полностью другой
  контент (другие тексты для чтения/аудирования, другие вопросы) — не
  те же задания, что в Start Diagnostic, ТЗ п. «Тест».
- **`diagnostic/forms.ts`** — диспетчер Form A/Form B
  (`formForKind("PROGRESS") → "B"`, всё остальное → `"A"`); через него
  теперь идёт вся логика прохождения диагностики (`scoring.ts`,
  `publicView.ts` рефакторены под параметр `form`).

## 2. Какой workflow реализован

**Преподаватель** (`backend/src/routes/teacherProgressCheck.ts`,
`frontend/.../teacher/progress/TeacherProgressCheckPage.tsx`) — ровно
шаги ТЗ: выбирает группу → видит ростер с отметкой «Старт пройден» →
выбирает студентов (чекбоксы, недоступны для уже назначенных) →
указывает начало периода (обязательно) и опционально окончание →
«Назначить» — система фиксирует назначение (`assignedAt`,
`assignedByTeacherId`).

**Студент** (`backend/src/routes/studentProgressCheck.ts`,
`frontend/.../student/progress/*`) — структурно не может запустить
диагностику сам: на маршруте студента нет ни одного `POST`, создающего
попытку — есть только чтение уже назначенной. До назначения видит
явный текст «...самостоятельно начать её нельзя», прямой запрос к
эндпоинту прохождения возвращает `404 NOT_ASSIGNED`. До начала периода —
`403 TOO_EARLY`. Каждая часть (анкета/тест) после завершения открывается
только на просмотр — как и Start Diagnostic/Start Profile, изменить
ответы или пройти повторно нельзя.

**Одно действие назначения = сразу обе попытки** (`DiagnosticAttempt` +
`QuestionnaireAttempt`, `kind="PROGRESS"`, один и тот же период) — в
одной транзакции: см. решение №1 в разделе 6.

## 3. Экран результата

`analytics/progressCheck.ts` (`getStudentProgressComparison`) — общий
расчёт, используемый и студентом, и преподавателем (один и тот же ответ,
проверено E2E побайтово через одинаковую разметку). Главный экран —
**Что было → Что стало → Что изменилось**:

- таблица **Навык | Старт | Сейчас | Изменение** для всех четырёх
  навыков (Grammar/Vocabulary/Reading/Listening) — из реальных
  сохранённых результатов Form A и Form B, не пересчитано «на глаз»;
- изменение **самооценки/мотивации/самостоятельности** — переиспользует
  без изменений формулы Этапа 6/7 (`computeSelfAssessment`/
  `computeMotivation`/`computeAutonomy`), применённые к ответам
  повторной анкеты;
- изменение **целей** (Q37) — добавились/остались/больше не выбраны, по
  разнице множеств кодов между Start и Progress;
- изменение **достижений** — количество подтверждённых достижений на
  момент завершения Start Diagnostic (`Achievement.verifiedAt <=
  startDiagnostic.completedAt`) против текущего количества — реальный
  фильтр по уже существующим датам, не выдуманное число.

## 4. История

Start Diagnostic/Start Profile никогда не изменяются модулем Этапа 10 —
Progress Check создаёт НОВЫЕ строки (`kind="PROGRESS"`), Start
(`kind="START"`) остаётся отдельной, неприкосновенной записью; проверено
явным тестом («Start Diagnostic не меняется после завершения Progress»).
Повторное назначение той же группе/студенту — идемпотентно
(`@@unique([studentId, groupId, kind])`, защита на уровне БД, не только
кода — проверено прямой повторной вставкой в обход HTTP).

## 5. Какие сценарии acceptance test пройдены

`backend/scripts/verify-progress-check.ts`, **44 проверки**, реальные
HTTP-запросы к работающему backend:

- Form A и Form B не пересекаются по содержанию заданий и покрывают
  одинаковый набор навыков и сопоставимую сложность;
- преподаватель — единственная роль, способная назначить (403 для
  студента); студент не может запустить сам (404 `NOT_ASSIGNED`), не
  может открыть раньше периода (403 `TOO_EARLY`), не может изменить
  результат или повторно открыть завершённую попытку на редактирование;
- полный workflow: назначение → прохождение анкеты и теста Form B →
  все дельты сравнения (навыки +50 п.п. на навык в тестовом сценарии,
  самооценка/мотивация/самостоятельность +2, цели: добавилась/осталась/
  пропала, достижения +1);
- сводка преподавателя и студента — идентичны (`JSON.stringify`
  сравнение);
- Start Diagnostic не изменяется после завершения Progress Check;
- защита от гонки на уровне БД (прямая повторная вставка — P2002);
- изоляция между преподавателями/студентами (404 на чужие
  группа/студент), неавторизованный доступ — 401.

Полная регрессия Этапов 1–9 (**415 проверок** суммарно по всем
`verify:*`, из них 44 — новые Этапа 10) — без изменений в продукте, всё
зелёное. Один заранее спланированный, не случайно найденный побочный
эффект: `teacherStudentProfile.ts` (Этап 7) уже содержал полностью
общую, key-агностичную логику отображения истории диагностики по
`kind` — с появлением реальных данных `PROGRESS` она заработала без
единой строчки изменений в самой логике; единственная правка —
исправление англоязычных подписей `DIAGNOSTIC_KIND_LABELS`
(`"Progress Check"` → «Промежуточная диагностика» и т.п.), которые были
написаны так с Этапа 7, но никогда не были видны на экране до этого
этапа (значения `PROGRESS`/`CREDIT` не встречались в БД).

**Реальный браузер (Playwright/Chromium)**, 34/34 проверки: полный
workflow «студент проходит стартовые анкету и диагностику → до
назначения видит "самостоятельно начать нельзя" → преподаватель
выбирает группу/студента/период, назначает → студент проходит повторную
анкету и тест Form B через настоящий UI (клики, ввод текста) → оба видят
одинаковый экран "Что было → Что стало → Что изменилось" → повторное
открытие завершённого теста не позволяет пройти заново»; отдельно —
мобильный сценарий (375px): обзорный экран и экран задания Form B без
горизонтального скролла.

### Найденные и исправленные проблемы

- Тестовый скрипт (не продукт): `verify-progress-check.ts` изначально
  передавал числовые значения (1–5) в качестве переопределений для
  вопросов Q15/Q16/Q21/Q22, ошибочно предположив тип `SCALE_1_5` — они
  оказались `SINGLE_CHOICE` с текстовыми значениями вариантов, а
  итоговый балл 1–5 вычисляется из них уже потом (`ordinalScore()`).
  Обнаружено по ответу backend (`INCOMPLETE`, эти 4 вопроса оставались
  незаполненными), исправлено передачей корректных строковых значений
  вариантов.
- E2E-скрипт (не продукт): проверка вступительных экранов повторной
  анкеты и теста Form B изначально ждала кнопку с текстом «Начать» —
  но такая кнопка с тем же текстом уже присутствует на экране обзора
  (для ещё не начатого теста), из-за чего проверка иногда захватывала
  разметку старой страницы за долю мгновения до реального перехода.
  Исправлено ожиданием текста, уникального именно для экрана-введения
  (например, «не сертификация CEFR»), а не текста кнопки.

## 6. Какие решения требуют подтверждения

1. **Одно назначение = сразу обе попытки** (тест + анкета,
   `progressCheck/service.ts`) — ТЗ описывает «назначает диагностику»
   как один workflow, а блок «Дополнительно» (изменение самооценки/
   мотивации/самостоятельности/целей) вычислим только из данных
   анкеты — без повторного анкетирования эти пункты пришлось бы либо
   не показывать, либо выдумывать. Решено назначать оба сразу одним
   действием преподавателя, одним периодом; сами тест и анкета
   остаются двумя независимыми сущностями/маршрутами (как и на
   Старте) — не смешаны.
2. **`periodEndAt` не блокирует прохождение после даты** — реализован
   как информационная метка (показывается преподавателю и студенту),
   без жёсткого запрета завершить диагностику позже. ТЗ явно запрещает
   только «пройти раньше срока»; ничего не сказано про верхнюю границу
   — решено не придумывать штраф/блокировку, которой нет в тексте.
3. **Изменение количества достижений** — вычислено как разница между
   количеством подтверждённых на момент завершения Start Diagnostic
   (`Achievement.verifiedAt <= startDiagnostic.completedAt`) и текущим
   количеством. Это реальный фильтр по уже существующим датам БД, а не
   изобретённое число — но точную методологию «на момент старта» ТЗ не
   определяет; выбранная интерпретация (по дате подтверждения
   достижения, а не по дате его добавления) задокументирована в коде
   `analytics/progressCheck.ts`.
4. **Повторное назначение уже назначенному студенту** — не создаёт
   вторую попытку и не позволяет изменить уже выставленный период
   (идемпотентный ответ `ALREADY_ASSIGNED`); изменение периода уже
   назначенной попытки в этой версии не поддерживается — по аналогии с
   «история не переписывается».

Автоматических педагогических рекомендаций на основе сравнения
Старт → Сейчас в этом этапе **не создано** — ни одной строки кода,
формирующей совет/рекомендацию преподавателю или студенту на основе
дельты показателей; экран показывает только сравнительные числа и
факты (см. раздел 3). Такая логика требует отдельного задания.

отслеживания прогресса, портфолио достижений и сопровождения зачёта.

## Реализовано

**Этап 1 — авторизация, роли, профили:**

- регистрация, вход, выход, восстановление доступа;
- роли: преподаватель, студент, администратор (архитектурно);
- разграничение доступа к данным на уровне backend (не только UI);
- профиль преподавателя и профиль студента;
- русскоязычная навигация с честными заглушками "в разработке" для
  ещё не реализованных разделов.

**Этап 2 — курсы, группы, код подключения:**

- учебные годы, курсы/дисциплины, группы (создание, открытие,
  переименование, архивирование);
- автоматический уникальный join-код группы (`ENG-XXXXX`) с показом,
  копированием, регенерацией и деактивацией;
- изоляция данных между преподавателями на уровне backend (404 на
  прямой доступ по id к чужой сущности).

**Этап 3 — подключение студента к группе:**

- присоединение по коду: превью группы (название, курс, учебный год,
  преподаватель) перед подтверждением;
- понятные раздельные ошибки — код не найден, отключён, просрочен;
- повторное подключение не создаёт дубликат membership.

**Этап 4 — START PROFILE (анкетирование, Q1–Q45):**

- 13 последовательных экранов, ветвление, индикатор прогресса,
  автосохранение, защита от потери данных, мобильная адаптация;
- `QuestionnaireAttempt` привязан к student/group/course/academicYear,
  исторические ответы не перезаписываются;
- ответы размечены для будущей аналитики (`indexGroup`), но сами
  индексы не считаются и студенту не показываются — только короткое
  «Анкетирование завершено.».

**Этап 5 — START DIAGNOSTIC (объективная проверка навыков):**

- отдельный от анкетирования модуль: Grammar, Vocabulary, Reading,
  Listening (32 задания), свои модели/маршруты/экраны;
- банк заданий хранится в коде backend — правильные ответы
  структурно не могут утечь клиенту;
- Listening — через Web Speech API (озвучка в браузере, без внешней
  инфраструктуры аудио);
- результат — числовой профиль по навыкам, без выдуманного
  CEFR-уровня (`diagnosticRange` остаётся `null` до утверждения
  матрицы порогов).

**Этап 6 — TEACHER DASHBOARD (рабочая панель преподавателя):**

- каскадные селекторы Учебный год → Курс → Группа; KPI-блок
  «Состояние группы» (6 плиток — диагностика, средний результат,
  мотивация, самостоятельность, квалификационные баллы, зачёт);
- «Требуют внимания» — многофакторная логика (не флагует по одному
  слабому показателю), с раскрываемым «Почему?»; «Возможности
  развития» — только показывает потенциал, не решает за
  преподавателя; ни в одном из блоков нет ранжирования студентов;
- таблица студентов (11 столбцов, поиск/фильтры/сортировка), на
  мобильном экране — карточки;
- профиль студента (переход «Открыть профиль») и заметки
  преподавателя (`TeacherNote`) — новые маршруты, та же изоляция по
  teacherId, что и everywhere else;
- Dashboard запрашивает только нужные для аналитики поля (не всю
  анкету и не сырые ответы диагностики) — агрегаты считаются один раз
  на backend, не дублируются на фронтенде;
- квалификационные баллы, зачёт, Progress Check — честно
  `implemented: false`/пустые состояния, модули не реализованы.

**Этап 7 — ПОЛНЫЙ ПРОФИЛЬ СТУДЕНТА:**

- 8 вкладок (Обзор/Диагностика/Анкета/Цели/Достижения/Зачёт/Progress/
  Заметки) — открывается из Dashboard («Открыть профиль»);
- Обзор — сильные стороны, зоны развития, потенциал (несколько меток
  одновременно), рекомендуемый фокус с обоснованием «Почему?»,
  сравнение самооценки с объективным результатом (только там, где
  Start Diagnostic вообще проверяет этот навык);
- Диагностика — история Start/Progress/Final и таблица навыков (6
  навыков, включая Письмо/Говорение с честным «Не оценивался», не 0%);
- Анкета — полные 45 ответов по 13 разделам, accordion, без кодов
  вопросов на экране;
- Цели — статус каждой цели (Q37) меняет только преподаватель, никогда
  не выставляется автоматически; история изменений сохраняется;
- Заметки — с типом (наблюдение/рекомендация/договорённость/важная
  информация/подготовка к мероприятию), история не удаляется;
- Обзор загружается лёгким запросом; полные ответы анкеты и полная
  история диагностики — только при открытии соответствующей вкладки;
- Достижения/Зачёт/Progress Check — честные заглушки «не реализовано»
  на момент Этапа 7, сами модули появились на Этапе 8.

**Этап 8 — ДОСТИЖЕНИЯ, ВНЕАУДИТОРНАЯ ДЕЯТЕЛЬНОСТЬ, КВАЛИФИКАЦИОННЫЕ БАЛЛЫ:**

- полный workflow: студент добавляет достижение (пошаговая форма,
  загрузка подтверждающего документа) → отправляет на проверку →
  преподаватель подтверждает (с баллом/без), запрашивает уточнение или
  отклоняет → квалификационный балл начисляется только явным решением
  преподавателя;
- ровно 1 балл за результативное мероприятие, не больше — защита от
  повторного начисления на уровне БД (уникальный индекс
  `QualificationPoint.achievementId`), не только в коде маршрута;
- обнаружение возможных дублей мероприятия (предупреждение, не
  блокирует) + отдельная жёсткая защита от начисления двух баллов за
  одно и то же мероприятие в момент подтверждения;
- портфолио (все подтверждённые достижения) и квалификационные баллы
  (только результативные) — разные, независимо считаемые понятия;
- `AchievementAuditLog` — полная история решений (кто/когда/что/
  причина);
- статус устной части зачёта (`qualification_points >= 5 →
  освобождён`) — единая функция расчёта, используется и в Teacher
  Dashboard, и в Student Profile.

**Этап 9 — МОДУЛЬ «ДИФФЕРЕНЦИРОВАННЫЙ ЗАЧЁТ»:**

- **Допуск (активный словарь)** — заявка (слов/описание/файлы любого
  формата/ссылка), подтверждается ТОЛЬКО явным решением преподавателя
  (Открыть → Подтвердить/Запросить уточнение/Отклонить), каждая
  повторная отправка — новая запись, история не переписывается;
- **Лексико-грамматический тест** — 10 вопросов из управляемого
  преподавателем банка (`CreditTestItem`), один вопрос на экран,
  свободные переход назад/смена ответа до завершения, автоматическая
  проверка, показ правильных ответов — по настраиваемой политике
  курса (не жёстко "всегда");
- **Устная часть** — 17 утверждённых тем (английские названия
  дословно), назначает только преподаватель, оценка по 6 критериям
  положения, предварительный результат — раскрытая эвристика с явной
  пометкой "подтверждает преподаватель", итоговую оценку преподаватель
  всегда подтверждает отдельным действием;
- **Освобождение от устной части** при 5+ квалификационных баллах —
  переиспользует расчёт Этапа 8, запись `OralAssessment(EXEMPTED)`
  сохраняется для истории даже когда беседа не проводилась;
- **"Итог" зачёта** — единая функция (`analytics/credit.ts`),
  реализующая точное IF/ELSE-дерево ТЗ: допуск → тест → баллы/устная
  часть → итог; ни один из трёх модулей (Start Diagnostic, Progress
  Check, Зачёт) не смешан с другими на уровне данных;
- экран «Зачёт» преподавателя — 8 сводных чисел, таблица с фильтрами,
  быстрый фильтр «5+ квалификационных баллов»; модуль полностью
  доступен с мобильного экрана для прохождения теста студентом.

**Этап 10 — ПРОМЕЖУТОЧНАЯ ДИАГНОСТИКА (PROGRESS CHECK):**

- сравнение **СТАРТ → СЕЙЧАС**: назначает только преподаватель (группа →
  студенты → период → «Назначить»), студент не может запустить сам,
  открыть раньше периода, изменить результат или повторно открыть
  завершённую попытку;
- **Form B** — новый, полностью отличный от Start Diagnostic набор
  заданий (32, тот же состав навыков/сложности) — не переиспользует
  вопросы Form A;
- одно назначение сразу создаёт и тест, и повторную анкету (одним
  периодом) — блок «Дополнительно» (самооценка/мотивация/
  самостоятельность/цели) вычислим только из данных анкеты;
- главный экран результата — **Что было → Что стало → Что изменилось**:
  таблица по 4 навыкам, изменение самооценки/мотивации/
  самостоятельности, изменение целей, изменение количества достижений;
  один и тот же расчёт показан и студенту, и преподавателю;
- Start Diagnostic никогда не перезаписывается — каждая диагностика
  хранится как отдельный snapshot (`kind = "START"`/`"PROGRESS"`);
- никаких автоматических педагогических рекомендаций на основе
  сравнения не создано — только сравнительные факты.

Writing/Speaking (как отдельный тест) — не реализован, следующие этапы.

## Технологический стек

- **Backend:** Node.js + Express + TypeScript, Prisma ORM (SQLite в
  разработке), JWT в httpOnly-cookie, bcrypt для паролей, zod для
  валидации.
- **Frontend:** React + TypeScript, Vite, React Router, Tailwind CSS.

## Структура репозитория

```
backend/    — API-сервер, схема БД (Prisma), скрипт проверки доступа
frontend/   — веб-приложение (React + Vite)
docs/       — спецификация продукта и отчёты по этапам разработки
```

## Быстрый старт (локальная разработка)

### Backend

```bash
cd backend
cp .env.example .env      # при необходимости отредактируйте JWT_SECRET
npm install
npm run prisma:migrate    # создаст SQLite-базу backend/prisma/dev.db
npm run dev                # http://localhost:4000
```

### Frontend

```bash
cd frontend
cp .env.example .env
npm install
npm run dev                # http://localhost:5173
```

Откройте `http://localhost:5173` — попадёте на страницу входа.

### Проверка разграничения доступа

После запуска backend (`npm run dev` в каталоге `backend`) выполните в
соседнем терминале:

```bash
cd backend
npm run verify:access
```

Скрипт создаёт двух преподавателей и двух студентов, реальными HTTP-
запросами проверяет, что каждый видит только свои данные и не может
получить доступ к чужому разделу напрямую (см.
[`backend/scripts/verify-access-control.ts`](backend/scripts/verify-access-control.ts)).

### Проверка изоляции Teacher Workspace (Этап 2)

```bash
cd backend
npm run verify:workspace
```

Создаёт двух преподавателей, каждый заводит учебный год → курс →
группу → join-код, и проверяет, что чужие сущности не видны в списках
и недоступны по id напрямую (см.
[`backend/scripts/verify-workspace-isolation.ts`](backend/scripts/verify-workspace-isolation.ts)).

### Проверка Student Onboarding (Этап 3)

```bash
cd backend
npm run verify:onboarding
```

просрочен), защиту от дублирования membership при повторном
подключении и изоляцию списка групп между студентами (см.
[`backend/scripts/verify-student-onboarding.ts`](backend/scripts/verify-student-onboarding.ts)).

Проверяет, что банк заданий отдаётся без правильных ответов, что

между студентами (см.

### Проверка Teacher Dashboard (Этап 6)

```bash
cd backend
npm run verify:dashboard
```

Создаёт группу с пятью студентами с заранее известными показателями

### Проверка полного профиля студента (Этап 7)

```bash
cd backend
npm run verify:student-profile
```

Создаёт студента с заранее известными сильными/слабыми сторонами,
барьерами, потенциалом и целями и проверяет: педагогический обзор
(сильные стороны/зоны развития/потенциал/рекомендации с обоснованием);
Обзор не содержит полных ответов анкеты и полной истории диагностики
(это отдельные, лениво подгружаемые маршруты); статус цели меняет
только преподаватель и пишет историю изменений; заметки с типом;
изоляцию между преподавателями на всех новых маршрутах (см.
[`backend/scripts/verify-student-profile.ts`](backend/scripts/verify-student-profile.ts)).

### Проверка достижений и квалификационных баллов (Этап 8)

```bash
cd backend
npm run verify:achievements
```

Реальными HTTP-запросами (включая настоящую multipart-загрузку файла)
проверяет все 7 acceptance-сценариев ТЗ (обычный участник — 0 баллов,
призовое место/публикация/победитель номинации — по +1, дублирование —
не более 1 балла суммарно, три результата одного мероприятия — 1 балл,
пять баллов — освобождение от устной части), полный workflow
(черновик → отправка → уточнение → правка → решение), защиту от
повторного начисления на уровне БД (прямая попытка в обход HTTP),
защиту от начисления балла за дубль, «Изменить статус» с отзывом
ошибочно начисленного балла, права доступа и интеграцию с Dashboard
(см. [`backend/scripts/verify-achievements.ts`](backend/scripts/verify-achievements.ts)).

### Проверка дифференцированного зачёта (Этап 9)

```bash
cd backend
npm run verify:credit
```

Реальными HTTP-запросами проверяет все 6 acceptance-сценариев ТЗ
(словарь не подтверждён → «Не допущен»; допущен, тест не пройден;
0–4 балла → устная часть обязательна; 5 баллов → освобождение;
обычное участие → 0 баллов; призовое место + публикация + диплом
одного мероприятия → 1 балл, не 3), полный workflow допуска
(отправка → «Открыть» → решение → повторная отправка после отказа,
история сохраняется), прохождение теста (свободная смена ответа до
завершения, лимит попыток, показ ответов по настройке курса),
назначение и оценку устной части (предварительный результат,
подтверждение), защиту от гонки на уровне БД (прямая попытка в обход
HTTP), изоляцию от Start Diagnostic/Progress Check и права доступа
(см. [`backend/scripts/verify-credit.ts`](backend/scripts/verify-credit.ts)).

### Проверка промежуточной диагностики (Этап 10)

```bash
cd backend
npm run verify:progress-check
```

Реальными HTTP-запросами проверяет: Form A и Form B не пересекаются по
содержанию и покрывают одинаковый набор навыков; назначить может только
преподаватель (403 для студента); студент не может начать сам (404
`NOT_ASSIGNED`), открыть раньше периода (403 `TOO_EARLY`) или изменить
результат/повторно открыть завершённую попытку; полный workflow
назначения → прохождения теста Form B и повторной анкеты → сравнение
Старт → Сейчас по всем показателям (навыки, самооценка/мотивация/
самостоятельность, цели, достижения); идентичность сводки у студента и
преподавателя; неизменность Start Diagnostic после Progress Check;
защиту от гонки на уровне БД и права доступа
(см. [`backend/scripts/verify-progress-check.ts`](backend/scripts/verify-progress-check.ts)).

### Проверка восстановления доступа (Этап 12)

```bash
cd backend
npm run verify:password-reset
```

Реальными HTTP-запросами (и точечной правкой БД для эмуляции истечения
срока) проверяет полный цикл `forgot-password` → `reset-password` →
вход новым паролем, невалидный и истёкший токен, одноразовость токена,
нейтральное сообщение (не палит факт регистрации email), отклонение
слабого пароля — и, отдельно, само исправление Этапа 11 (CRITICAL):
без явного `EXPOSE_DEV_PASSWORD_RESET_TOKEN=true` токен нигде не
появляется в ответе API
(см. [`backend/scripts/verify-password-reset.ts`](backend/scripts/verify-password-reset.ts)).

### Проверка целевых сценариев QA-аудита (Этап 11)

```bash
cd backend
npm run verify:qa-audit-security
```

Закрывает пробелы в покрытии, обнаруженные при финальном QA-аудите:
IDOR на attempt-id Start Diagnostic и анкеты (студент угадывает id
чужой попытки), попытки подмены сервер-вычисляемых полей в теле
запроса (квалификационный балл, финальная оценка устной части,
корректность ответа диагностики)
(см. [`backend/scripts/verify-qa-audit-security.ts`](backend/scripts/verify-qa-audit-security.ts),
[`docs/STAGE_11_QA_REPORT.md`](docs/STAGE_11_QA_REPORT.md)).

## Пилотный тестовый набор (Этап 13)

Постоянный, воспроизводимый набор тестовых аккаунтов для пилотного
тестирования — Teacher Test Account, Student A/B/C, тестовая группа с
уже реалистично заполненными данными. Явно отделён от любых реальных
данных (домен email `.test`, маркер «(ПИЛОТ-ТЕСТ)» в каждом названии)
— подробности и полный список сценариев в
[`docs/STAGE_13_PILOT_TEST_REPORT.md`](docs/STAGE_13_PILOT_TEST_REPORT.md).

```bash
cd backend
npm run pilot:setup       # создать/найти Teacher + Student A/B/C + группу (идемпотентно)
npm run pilot:scenarios   # прогнать сценарии (достижения, зачёт, Progress Check)
npm run pilot:reset-scenarios  # сбросить сценарии для повторной демонстрации
```

## Переменные окружения

См. `backend/.env.example` и `frontend/.env.example`. `.env` файлы не
коммитятся в репозиторий.

`EXPOSE_DEV_PASSWORD_RESET_TOKEN` (backend, по умолчанию выключен) —
только для локальной разработки без email-провайдера: возвращает
токен восстановления пароля в ответе API вместо реальной отправки
письма. **Никогда не включать в продакшене.**
